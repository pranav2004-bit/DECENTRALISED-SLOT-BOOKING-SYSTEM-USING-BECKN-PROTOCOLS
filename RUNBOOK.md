## Running the 5-Participant Network Locally (livetracker7.md)

The local `docker compose` stack now runs **5 real, independently-identified participants** — 3 single-domain BPPs and 2 all-domain BAPs, all the same 2 codebases (`BPP/backend`+`BPP/web`, `BAP/backend`+`BAP/web`), differentiated purely by config. See [ARCHITECTURE.md](ARCHITECTURE.md)'s "Multi-Participant Network Topology" for the full design; this section is the operational how-to.

| Participant | Brand | Backend service | Web service | Backend port | Web port |
|---|---|---|---|---|---|
| BPP-Beauty | StyleNest | `bpp-backend` | `bpp-web` | 8002 | 3001 |
| BPP-Medical | CareNest | `bpp-medical-backend` | `bpp-medical-web` | 8004 | 3003 |
| BPP-Automotive | AutoCare | `bpp-automotive-backend` | `bpp-automotive-web` | 8005 | 3004 |
| BAP-X | OnSlot | `bap-backend` | `bap-web` | 8001 | 3000 |
| BAP-Y | GoFetch | `bap-y-backend` | `bap-y-web` | 8006 | 3005 |

**Bring the whole network up:** `docker compose up -d` — this also starts `registry`, `beckn-gateway`, the shared `bpp-cache`/`bap-cache` Redis containers (each BPP-family/BAP-family instance uses its own DB index on the shared container — see ARCHITECTURE.md, not 5 separate Redis containers), and `bpp-medical-worker`/`bpp-automotive-worker`/`bpp-worker` (each BPP instance's own audit-log/metrics/WebSocket-broadcast consumer — the existing "rebuild backend+worker together" lesson below applies to all 3 pairs now, not just the original one).

**On a resource-constrained machine, use `./staged-up.sh` instead:** starting every container at once is a real CPU/RAM spike that can push a low-memory host into swapping and crashing — root-caused live on an 8GB/12-core laptop capped to a 4GB/2-core Docker VM (2026-08-30). `staged-up.sh` brings the stack up in 5 waves — caches, then Registry+Gateway, then the 5 backends (one at a time, not together — 5 starting simultaneously still exceeded the healthcheck probe's timeout under CPU contention, confirmed live 2026-09-01), then the 3 workers, then the 5 frontends — using `docker compose up -d --wait` so each wave genuinely blocks on health before the next starts. Functionally identical end state to `docker compose up -d`; only the startup ordering differs. `./test-staged-up.sh` validates the script itself (syntax, and that every service in `docker-compose.yml` is staged exactly once — catches drift if a participant is ever added/renamed and a stage is forgotten) — run it after editing either file.

**Postgres moved to Neon, 2026-09-02 — local stack is 18 containers, not 24.** All 6 databases (registry, bap, bpp, bpp_medical, bpp_automotive, bap_y) now live on Neon (managed Postgres), removing all 6 local Postgres containers — real relief for the same CPU/RAM contention above. Each service's own `.env` `DATABASE_URL` points at its Neon connection string instead of a local container; nothing in `docker-compose.yml`, app code, or `staged-up.sh` needed further changes beyond removing the 6 db services and their `depends_on` entries.

Two real things found live during this migration, worth knowing before re-deriving them:
- **BPP-family instances need Neon's *unpooled* connection string (no `-pooler` in the hostname), not the pooled one.** `bpp/settings.py` sets `DATABASES["default"]["OPTIONS"] = {"options": "-c statement_timeout=... -c idle_session_timeout=..."}` (a real, deliberate defense-in-depth setting, not something to remove) — Neon's pooled endpoint (PgBouncer, transaction mode) only forwards a small allowlist of startup parameters and rejects this with "unsupported startup parameter in options: statement_timeout". BAP doesn't set this OPTIONS block, so BAP-X/BAP-Y stay on the normal pooled connection string.
- **A database's first-ever connection attempt after being idle can fail** with what looks like a DNS error (`could not translate host name ... to address`), then succeeds immediately on a plain retry — consistent with Neon's free-tier "scales to zero when inactive" behavior waking the compute back up, not a real config problem. Confirmed repeatedly (3 of 6 databases hit this on their first connection, all 3 succeeded on the very next attempt with zero changes). If a fresh `staged-up.sh` run fails on a backend with this exact symptom, just retry that one service (`docker compose up -d --wait <service>`) before assuming something is actually broken.

**Automatic retry added, 2026-09-03 (`shared/resilient_db`):** the above was previously a manual "just retry the command" workaround — Registry, BAP, and BPP's `DATABASES["default"]["ENGINE"]` now point at `resilient_db` (not `django.db.backends.postgresql` directly), which retries a database's *first* connection attempt up to 3 times with a 2s backoff before giving up, entirely automatically. This is a stopgap, not the real fix — the real permanent fix is a paid Neon plan (always-on compute, never suspends), not affordable right now. A genuinely wrong credential/database still fails, just ~4-6s slower, never silently masked. Real bugs hit and fixed while wiring this in: `ENGINE` must be `"resilient_db"`, not `"resilient_db.base"` (Django appends `.base` itself — the double-suffix version raises `ModuleNotFoundError: No module named 'resilient_db.base.base'`); and each app's Dockerfile needs its own explicit `COPY shared/resilient_db ./shared/resilient_db` line (no wildcard `COPY shared/`, confirmed by grep against all three Dockerfiles) or the import fails with a plain `ModuleNotFoundError: No module named 'resilient_db'` despite the file genuinely existing on the host. Verified live: all 4 of `resilient_db`'s own tests pass, plus Registry (21/21), BAP (233/233), and BPP (401/402, the 1 failure a pre-existing timing-sensitive test confirmed unrelated by re-running it alone) all pass with the new engine wired in.

**Rebuilding after a code change:** the existing "images, not bind-mounts" and "backend+worker share a build, rebuild both together" lessons below apply per-instance now — e.g. a `BPP/backend` change needs `docker compose build bpp-backend bpp-worker bpp-medical-backend bpp-medical-worker bpp-automotive-backend bpp-automotive-worker` (all 3 pairs, since all 3 build from the identical Dockerfile/context) before `docker compose up -d` for whichever of those 6 you actually need running with the new code.

**A real gap found and fixed live standing up this topology (`livetracker7.md` Phase 2, 2026-08-22): a fresh multi-container DB pair (a new instance's `-backend` + `-worker`, both racing `migrate` against a genuinely empty database at once) can crash on first boot** — confirmed live for both `bpp-medical-*` and `bpp-automotive-*` (`relation "inventory_core_rating" already exists` / a `pg_type` duplicate-key error), never hit before because the original `bpp-backend`/`bpp-worker` pair always shared an already-migrated dev volume. Fixed permanently: `entrypoint.sh` now runs `migrate_locked` (a Postgres session-level advisory lock around `migrate`) instead of plain `migrate --noinput`, so this is a non-issue going forward for any new instance — mentioned here only so a future from-scratch stand-up of a 6th/7th instance doesn't need to re-discover it.

**Registry onboarding for a new instance** (already done for all 5 above; only needed again if you wipe Registry's own DB or add a 6th participant): `docker compose exec <backend-service> python manage.py onboarding_approve <domain-code>` then `onboarding_subscribe <domain-code>`, one call per domain the instance should serve (3 calls for a BAP, 1 for a single-domain BPP). To **narrow** an existing participant's scope (e.g. if BPP-Beauty needed to drop a domain again), there is a real command for it now — `docker compose exec registry python manage.py deactivate_participant <subscriber_id> <domain-code>` — added in `livetracker7.md` Phase 2 (Registry had no such capability before).

**Seeding demo data on a fresh BPP instance:** through the real API only, never direct DB inserts — `POST /api/v1/auth/csrf` → `/api/v1/auth/signup` → `/api/v1/auth/login` → `POST /api/v1/resources` → `POST /api/v1/resources/<id>/availability`. For an Automotive instance specifically, seed **two** resources (`resource_type: "bay"` and `resource_type: "mechanic"`) with the **identical** `range_start`/`range_end`/`times` on their availability calls — the multi-resource pairing (`automotive_adapter.find_paired_resource`) only finds a match at a given timestamp if both resources genuinely have a slot there.

## Known Operational Facts (filled in as Phase 2–4 progress)

- The Registry is a single point of trust for the whole network. **Confirmed live in Phase 4.2** (not just theorized): stopping the Registry container and hitting Gateway's `/search` returns a clean `500 INTERNAL_ERROR` (fails closed, no crash) — but takes **~19 seconds** to fail, because `resilient_http`'s retry policy re-attempts DNS resolution on a now-unreachable hostname several times before giving up. If Registry-outage symptoms include slow (not fast) failures elsewhere, this is why — it is not a hang or a deadlock.
- **Fixed and confirmed live (2026-07-16):** the circuit breaker previously did not trip across gunicorn worker processes — 5 consecutive real failures against a stopped Registry, sent to Gateway's 2-worker container, never failed fast, each still took the full ~19s retry-then-DNS-fail path. Root cause was the same as the per-worker metrics/rate-limit undercounting below, applied to a new component: `ResilientHttpClient`'s circuit breaker state was a module-level singleton, so each gunicorn worker kept its own independent breaker. **Fix:** `RedisCircuitBreaker` (`shared/resilient_http/circuit_breaker.py`) shares state via Redis. Reverified live: attempts 1–5 against a stopped Registry each took ~19s, attempt 6 onward failed in ~0.3s with `CircuitOpenError`. Active unconditionally for BAP/BPP (required Redis); active for Gateway **only when `CACHE_ENABLED=true`** (the `gateway-cache` service stays an optional `[BETA]`-profile service, `docker compose --profile with-gateway-cache up`) — with the cache disabled (the default), Gateway's breaker falls back to the old per-worker in-memory behavior above. Registry's own outbound client (site-verification fetch, on_subscribe dispatch) was intentionally left on in-memory-only — that path wasn't part of the tested finding and Registry has no Redis dependency today.
- Recovery is fast and automatic: once Registry comes back, the very next request through Gateway succeeds in under 1 second — no manual restart or cache-clear needed anywhere.
- Rate limits: Subscribe 10 req/min, Lookup 7,600 req/min (per [protocol_compliance_notes_v1.1.md](protocol_compliance_notes_v1.1.md) §B.6) — a sudden spike in `RATE_LIMITED` errors against the Registry is expected behavior under abuse/misconfiguration, not a Registry bug.
- Key rotation has no dedicated endpoint — it's a re-`/subscribe` call with a new `key_pair` (§B.4). If a rotation appears "stuck," check whether the new Subscribe call actually completed the on_subscribe challenge, not just whether it was sent. **As of Phase 4.3, rotation must be signed with the CURRENTLY REGISTERED key, not the new one being submitted** — a re-Subscribe that gets `401 UNAUTHORIZED` is very likely signed with the wrong (new) key; this is by design (see Security below), not a bug.
- **Registry's `/subscribe` and `/lookup` now require a real signed `Authorization` header (Phase 4.3)** — an unauthenticated or wrongly-signed call to either gets `401 UNAUTHORIZED`. Confirmed live. First-time Subscribe is verified against the key being submitted (proof-of-possession); re-Subscribe is verified against the key already on file.
- **Known, protocol-consistent limitation, not a bug:** a validly-signed request can be replayed as-is within its signature's `created`→`expires` window (confirmed live — the same signed Lookup call succeeded twice in a row). The confirmed Authorization scheme has no nonce field, only a time window, so this is a characteristic of the real protocol design, not a gap introduced here. Mitigated by the short (~30s) window used throughout this codebase, not eliminated.
- **A BPP/BAP's own local `OnboardingStatus` row can get stuck at `UNDER_SUBSCRIPTION` even after Registry genuinely subscribes it — root-caused and fixed live during Phase 4.2.** Registry's own `handle_subscribe()` dispatches the on_subscribe challenge *synchronously, nested inside* its handling of the `/subscribe` call itself — meaning `handle_on_subscribe()` (the only code path that ever sets a row to `SUBSCRIBED`) can run and complete *before* `registry_client.subscribe()` even returns. `handle_on_subscribe()`'s own bulk `.filter(status=UNDER_SUBSCRIPTION).update(...)` only matches a row that is *already* `UNDER_SUBSCRIPTION` — but `submit_subscribe()` used to only write that status *after* the Registry call returned, so at the exact moment the nested challenge fired, the row was still whatever `approve()` had left it at (`AWAITING_APPROVAL`), never matching the filter at all. The challenge itself still succeeded (Registry's own `Participant.status` correctly shows `SUBSCRIBED` — that's the network's authoritative record, not the local mirror), but the local row silently never got the memo, for every domain, every time, going back to when this code was first written. **Fix (both `BPP/backend/core/onboarding_service.py` and `BAP/backend/core/onboarding_service.py`):** `submit_subscribe()` now marks its row `UNDER_SUBSCRIPTION` *before* calling Registry, not after — so by the time the nested challenge fires, `handle_on_subscribe()` has a real row to match. Confirmed live: re-running `onboarding_subscribe BECKN:AUTO01` after the fix reached `SUBSCRIBED` locally on the very first attempt, no retries needed, matching Registry's own authoritative state. If a domain's local status still looks stuck at `UNDER_SUBSCRIPTION`, check Registry's own `Participant.status` directly first — the network is very likely already correct, and this is a stale-local-mirror display issue, not a routing problem.
- **Real gap found and fixed live (Phase 4.7, 2026-07-29): running `pytest` against this docker-compose stack used to silently zero out real business-metrics counters and log out every real session.** `BAP/backend/core/conftest.py`'s (and BPP's identical `core/conftest.py`) autouse `_clear_rate_limit_cache` fixture calls `cache.clear()` before/after every test, needed to isolate §3.7's Redis-backed rate limiters between test runs — but `bap/settings.py`/`bpp/settings.py`'s `CACHES["default"]["LOCATION"]` pointed at the exact same Redis DB (`bap-cache:6379/0` / `bpp-cache:6379/0`) the live dev server's business-metrics counters and sessions live in, with no separate test database. Confirmed live: seeding a real counter in Redis DB 0, then running one BAP test file, left `redis-cli -n 0 KEYS '*'` completely empty afterward. **Fixed** in both apps' `settings.py`: `CACHES["default"]["LOCATION"]` now resolves to Redis DB 15 when the existing `TESTING = "pytest" in sys.modules` flag is set, real DB 0 otherwise — tests keep a real Redis-backed cache (preserving the atomic-`INCR` concurrency guarantee the concurrency tests below depend on), just in a DB the dev server never touches. If a real dev/demo dashboard ever again shows suspiciously-zeroed counters or unexpectedly logged-out sessions right after a test run, this is the class of bug to check for first — confirm which Redis DB index the running server vs. the test process actually points at.
- **Confirmed live (Phase 3 Exit, 2026-07-24): don't stack overlapping `docker compose up --build` commands on this repo's monorepo-context images.** Running two or three at once (impatience with the slow build — `context: .` at the repo root, plus a Windows/OneDrive-synced filesystem, makes a rebuild take several minutes even for a one-line settings change) caused a real, if fully recoverable, incident: a Gateway gunicorn worker was OOM-killed under the combined memory pressure, `bap-backend`'s old container left a zombie process Docker couldn't signal normally (`docker rm` even needed a beat to work), and two overlapping recreate attempts raced on the same container name, briefly leaving `registry-1` removed entirely with orphaned `<hash>_beckn-<service>-1` placeholders in its place. Recovery was straightforward once isolated to one command at a time: `docker rm -f` the stuck container, `docker rm` the orphaned placeholders, then a single clean `docker compose up -d`. No data was lost in either incident — only the two stateless app containers were ever touched, never their DB containers. **Lesson: issue one `docker compose build`/`up` at a time on this repo and wait for it, even when it feels slow — parallel builds don't parallelize the actual work here, they just contend for the same CPU/memory and occasionally corrupt container state.**
- **Confirmed repeatedly during `livetracker3.md`'s own work (Phases 8–10): the app containers are built images, not bind-mounted to live source.** `docker compose exec bap-backend`/`bpp-backend python -m pytest` runs whatever code was baked into the image at the last `docker compose build`, not the current working-tree files — editing a `.py` file and immediately running tests inside the running container silently exercises the *old* code (confirmed live: a new test file wasn't even collected by pytest until the image was rebuilt). **Lesson: after any backend code change, `docker compose build <service>` then `docker compose up -d <service>` before trusting an in-container test run** — a clean pass against a stale image is not evidence of anything.
- **A sharper version of the lesson above, found live (`livetracker6.md` §2.2/§2.3, 2026-08-03): `bpp-worker` builds from the identical Dockerfile/context as `bpp-backend` but has no `image:` override in `docker-compose.yml`, so Compose auto-assigns it its own, separate image tag (`beckn-bpp-worker`, distinct from `beckn-bpp-backend`) despite sharing a build context.** Running `docker compose build bpp-backend` alone — the natural thing to do after a backend code change — never rebuilds `bpp-worker`, and `docker compose up -d --force-recreate bpp-worker` alone does **not** rebuild it either (force-recreate only recreates the *container* from whatever image is already tagged; it doesn't invoke a build). The real running worker silently kept processing events with stale code for an extended period before this was caught — confirmed by diffing the actual `bpp/settings.py` content inside the running `bpp-worker` container against the source, not by inference. **Lesson: any change touching code `bpp-worker` runs (anything under `BPP/backend/core/events_worker.py`'s own `DISPATCH` table or its consumers) needs an explicit `docker compose build bpp-backend bpp-worker` — both named — followed by `docker compose up -d --force-recreate bpp-backend bpp-worker`, never just one service assumed to cover the other.** If a new event consumer or DISPATCH-table wiring change appears to silently do nothing in the real running stack despite passing tests, check `bpp-worker`'s own in-container source first, the same way §2's fix above was actually found.
- **Real gap found and fixed live (`livetracker3.md` §8, 2026-08-01): BPP's own Postgres connections could leak indefinitely, confirmed live via `pg_stat_activity` showing connections `idle`/`ClientRead` for 6+ minutes with no query running.** Root cause: a request's ASGI task getting cancelled after its DB work completed but before Django's own connection cleanup ran, orphaning the connection with nothing bounding how long it could sit open. **Fixed:** `BPP/backend/bpp/settings.py`'s `DATABASES["default"]["OPTIONS"]` now sets `-c statement_timeout=15000 -c idle_session_timeout=120000` — Postgres itself now reclaims an abandoned connection within 2 minutes regardless of why it leaked, rather than relying on the leaking side to ever clean up. If BPP's own DB connection count looks abnormally high, this is the mechanism that should already be bounding it; a still-growing count despite this means a genuinely new leak source, not a recurrence of this one.
- **Found live during `livetracker3.md`'s tracker-wide regression sweep (2026-08-02): the `statement_timeout=15000` above can also trip during `pytest`'s own `CREATE DATABASE test_bpp` step under heavy concurrent host load**, not just against a genuinely slow application query — running BPP's, BAP's, Registry's, and Gateway's full suites all at once on one machine produced a real `canceling statement due to statement timeout` error creating the test database; the identical suite re-run in isolation immediately after passed clean (347/347), confirming host CPU contention as the cause, not a code regression. **Lesson: don't run this repo's several-minutes-long backend test suites fully concurrently on a single dev machine — run them one at a time, or expect an occasional false-failure on `bpp-backend` specifically that a clean isolated re-run will clear.**
- **Confirmed live (2026-08-02): a stopped-then-restarted Prometheus/Grafana pair can fail to come back up with `failed to set up container networking: network <id> not found`** if the compose network was recreated at some point while they were stopped (e.g. by an unrelated `docker compose down`/`up` cycle on other services) — their container definitions still reference the old, now-gone network ID. **Fix:** `docker compose rm -f prometheus grafana` then `docker compose up -d prometheus grafana` — this recreates both containers against the current network rather than trying to reuse the stale one. No data loss (their volumes are untouched by `rm -f`, only the containers are removed).
- **Real gap found and fixed live (`livetracker3.md` §10.1, 2026-08-02): `trigger_cancel()` used to unconditionally wipe `cancelled_order`/`cancelled_error` on every call, including a retried call against a booking already successfully cancelled.** If that retry's own dispatch then failed, the evidence of the first, genuine cancellation was silently lost — the customer's own booking-history list (§9.1) would then incorrectly show a cancelled booking as still Active, with no way to tell from the data alone that a cancellation had ever succeeded. Fixed: `trigger_cancel()` now short-circuits to a no-op success the moment it sees `cancelled_order` already set, before touching either field or dispatching anything. If a customer ever reports "I cancelled but it still shows as active," check whether `cancelled_order` is genuinely null in the DB (a real, different bug) versus a stale frontend cache — this specific double-submit class of data loss is now closed at the source.
- **New single point of failure introduced (`livetracker4.md` §2.1, 2026-08-02): audit-log writes, business metrics, and WebSocket broadcasts for BPP now depend entirely on the separate `bpp-worker` process staying alive** — they used to fire inline, in the same request, with no separate process to go down. If a booking action's customer-facing outcome still looks correct but audit logs/dashboards/live availability updates stop appearing, **check `bpp_event_bus_worker_alive` first** (metrics table above), then `docker compose ps bpp-worker` / `docker compose logs bpp-worker` directly. `restart: unless-stopped` (`docker-compose.yml`) recovers a crash automatically; a container that's `Up` but `bpp_event_bus_worker_alive=0` means a genuine hang, not a crash. Events published while the worker is down are **not lost** — they sit on the real queue (`bpp_event_bus_dlq_length`'s own metric neighbor, though that specifically tracks the DLQ, not the main queue) and are processed the moment the worker comes back, via `recover_orphaned()` at its own startup.

## Registry Metrics & Alerting Thresholds (Phase 2.6)

`GET /metrics` on the Registry exposes real, live counters (not placeholders — see `core/metrics.py`):

| Metric | What it means | Suggested alert threshold |
|---|---|---|
| `registry_requests_total{metric="subscribe_errors_total"}` | Malformed/invalid Subscribe attempts | Sudden spike → possible misbehaving client or attack; investigate before assuming abuse |
| `registry_requests_total{metric="verify_failures_total"}` | Challenge replay/expiry/mismatch on on_subscribe | Sustained rate > a few per minute from one participant → likely a broken integration on their end, not ours |
| `registry_requests_total{metric="verify_successes_total"}` vs `subscribe_requests_total` | Conversion rate from Subscribe to actually reaching `SUBSCRIBED` | A large, persistent gap suggests participants are failing onboarding — worth proactive outreach, not just a technical alert |
| `registry_request_latency_seconds_sum / _count` (per `subscribe`/`lookup`) | Average latency per endpoint | No fixed number yet — no real traffic baseline exists at foundation stage; set a threshold once Phase 3 onboarding generates real traffic to baseline against, not before (avoids alerting on a made-up number) |
| Rate of HTTP `429` responses | Rate limiting engaging | Expected occasionally under legitimate retry storms; sustained high rate from one IP → likely abuse, correlates with `rate_limit.py`'s per-IP counters |

**Honest limitation carried from `rate_limit.py`/`metrics.py`:** both are in-process (LocMemCache/module-level), so with multiple gunicorn workers the true totals are undercounted per worker unless each worker's `/metrics` is scraped and summed independently. Acceptable at `[MVP]`/`[PILOT]` single/low-worker scale; revisit with shared Redis-backed counters before `[BETA]` multi-worker production.

**A real local dashboard exists as of 2026-07-17**: `docker compose --profile with-monitoring up -d` starts Prometheus (`monitoring/prometheus.yml`, scrapes all four apps' `/metrics` every 15s) and Grafana (`localhost:3002`, anonymous viewer access enabled for local dev, admin/admin for the provisioned account) with a pre-loaded 5-panel dashboard (`monitoring/grafana/dashboards/beckn-overview.json`) built from exactly this table. Confirmed live: all 4 scrape targets `up`, real Registry traffic visible in the dashboard within one scrape interval. This was previously described as blocked on "real cloud infrastructure" — that was incorrect; nothing here needs anything beyond `docker-compose`. What's still genuinely not set is the *alert threshold* for latency specifically (row above) — dashboards existing doesn't manufacture the missing real-traffic baseline.

**Confirmed live, not just theorized:** during Phase 2 Exit's real Docker container test (gunicorn `--workers 2`), two `/subscribe` calls landed on different worker processes, and a single `/metrics` scrape only showed one of them — live proof of the documented per-worker in-memory counter limitation above. Not a bug to fix at `[MVP]`; a real data point confirming the `[BETA]` Redis-backed-counters item is worth prioritizing once multi-worker production traffic is real.

## Beauty Booking Business Metrics & Alerting Thresholds (livetracker2.md §3.10)

`GET /metrics` on BAP exposes `bap_booking_funnel_total{stage=...}`, and on BPP `bpp_booking_lifecycle_total{event=...}` — both real, live counters (see each app's own `core/metrics.py`), same exposition format as Registry's table above:

| Metric | What it means | Suggested alert threshold |
|---|---|---|
| `bpp_booking_lifecycle_total{event="confirmed"}` / `(...{event="confirmed"} + ...{event="hold_expired"})` | Booking success rate — directly measures `project_details.md`'s own 95% KPI | Below 95% sustained → investigate; this is the one metric in this table with an externally-given target, not a guessed one |
| `bpp_booking_lifecycle_total{event="hold_expired"}` / `...{event="hold_created"}` | Reservation-hold expiry rate — real `HELD` reservations whose Redis TTL lapsed before the customer confirmed | No fixed number yet — no real traffic baseline exists at foundation stage; a sustained high rate is still worth a look regardless (either a confusing UI flow or a customer being deliberately slow/abusive, see §3.7's own hold-cap reasoning) |
| `bpp_booking_lifecycle_total{event="cancelled"}` / `...{event="confirmed"}` | Cancellation rate | No fixed number yet — same honest no-baseline rule as latency in the Registry table above |
| `bap_booking_funnel_total{stage="search_triggered"}` vs `{stage="confirm_succeeded"}` | Search-to-confirm conversion funnel — full drop-off across all 4 stages | Not itself an alert condition (most searches never convert, ordinary browsing) — a dashboard/trend signal, not a threshold |
| `bpp_booking_lifecycle_total{event="hold_created"}` with zero matching `confirmed`/`hold_expired` over a long window | A hold created but never resolved either way — would indicate the "opportunistic expiry detection" design (§1.3) isn't actually being exercised by anything in production | Investigate if sustained; see the honest gap noted below about `release_expired_hold()`'s real call sites |
| `bpp_event_bus_dlq_length` (livetracker4.md §2.1/§2.3, added 2026-08-02) | Real, live count of events currently sitting in BPP's DLQ (`EventBus.dlq_length()` — direct Redis `LLEN`, not an estimate) | **Any sustained non-zero value** → a real, unresolved failure is accumulating; `docker compose exec bpp-backend python manage.py requeue_dlq --peek` to see what and why, `--event-id <id>` to requeue one after understanding the cause — never blindly requeue in bulk (see that command's own `--help`, matching this table's own DLQ-doesn't-retry-forever framing) |
| `bpp_event_bus_worker_alive` (livetracker4.md §2.1, added 2026-08-02) | 1 if `run_event_worker`'s own heartbeat (a short-TTL Redis key refreshed once per loop iteration) is fresh, 0 if it's expired or was never set | **0 for more than ~30s** → the worker is dead or hung; audit logging, business metrics, and WebSocket broadcasts have **all** silently stopped (they have no other producer since the 2026-08-02 cutover — see the Known Operational Facts entry below). Check `docker compose ps bpp-worker` / `docker compose logs bpp-worker`; `restart: unless-stopped` should already be recovering a crash on its own, so a sustained 0 more likely means a hang, not a crash-loop |

**Real, honest gap found during §3.10's own implementation, not glossed over:** `inventory_core.reservation.release_expired_hold()` has **zero production call sites** as of this phase (confirmed by direct grep — only test files call it) — nothing in BPP's current code opportunistically reconciles an expired hold the way §1.3's own design intended. `hold_expired` above is therefore measured a different, still-real way: BPP's `confirm_service.dispatch_on_confirm` already raises/catches a `ValidationError` exactly when a customer's real `/confirm` arrives after their hold's TTL has lapsed (`confirm_hold()`'s own `is_active()` check) — that's the genuine, already-firing signal used, not a fabricated one. The `release_expired_hold()` dead-code gap itself is noted here for future reconciliation work (§3.11's own reconciliation-job bullet is the natural place to eventually wire a real caller), not silently fixed as an unrequested side effect of this section.

**Unlike Registry's own metrics above, BAP's/BPP's new business counters are genuinely Redis-backed from the start** (`shared/django_observability/metrics.py`, reusing the same `django_redis`-configured cache `rate_limit.py` already proved), consistent with §3.7's rate-limiter decision — the per-worker in-process undercounting limitation documented above for Registry does **not** apply here. Registry's own existing gap is not retroactively fixed by this section; it stays its own accepted, already-documented limitation. BAP and BPP currently run single-process `daphne` in this dev deployment (not multi-worker `gunicorn` like Registry/Gateway) — real cross-process correctness for these new counters is instead demonstrated directly: two independent Python processes incrementing the same Redis-backed counter concurrently produce one correct combined total, the property that actually matters, rather than a claim tied to a WSGI server this project's current BAP/BPP deployment doesn't run.

**A real local dashboard exists as of 2026-07-23**: the same `docker compose --profile with-monitoring up -d` Prometheus/Grafana stack now scrapes these new counters too (no separate opt-in needed — BAP/BPP were already scrape targets), with four new panels appended to `monitoring/grafana/dashboards/beckn-overview.json` (booking success rate, hold-expiry rate, cancellation rate, and the search-to-confirm funnel).

## BAP/BPP Rate Limit Thresholds & Hold-Abuse Cap (livetracker2.md §3.7)

Real, currently-configured values (`shared/rate_limit`'s `@rate_limit(limit_per_minute=..., scope=...)` decorator, confirmed by direct grep against both apps' `core/views.py` — not estimated):

| App | Endpoint (`scope`) | Limit |
|---|---|---|
| BAP | `signup`, `login` | 5/min |
| BAP | `search` | 20/min |
| BAP | `select`, `init`, `confirm`, `status`, `cancel`, `update`, `track`, `rating`, `support` | 10/min each |
| BPP | `business-signup`, `business-login` | 5/min |
| BPP | `resource-create`, `resource-assign-staff`, `resource-availability-create`, `resource-availability-block` | 30/min each (per authenticated account, not per IP) |
| BPP | `staff`, `locations` | 20/min each (per authenticated account) |

A real `429` on any of the above is expected, working behavior under a genuine burst (a customer double-clicking Confirm, a business bulk-creating slots), not itself an incident — only a *sustained* high rate from one actor is worth investigating (same "don't over-react to rate limiting itself" posture as Registry's own thresholds above).

**Reservation-hold abuse cap** (`BAP/backend/core/select_service.py`'s `MAX_CONCURRENT_HOLDS = 3`): a customer (or anonymous `client_ip`) may have at most 3 real "in-flight" transactions (`selected_order` set, not yet `confirmed_order`/`cancelled_order`) at once — a 4th concurrent `/select` gets a clean `429 Too many concurrent reservation holds`. This is the real, live-exploitable-DoS mitigation §3.7 built (mass-holding every available slot across many `transaction_id`s without ever confirming) — if this error surfaces in real usage, it means one actor is genuinely holding 3 unconfirmed selections already, not a bug in the counter itself.

## Beauty Business-Layer Resilience & Failure Injection (livetracker2.md §3.11)

All scenarios below run live against the real Docker stack on 2026-07-23, following the exact precedent set by the Registry-outage findings above — actual observed timing/behavior, not theorized.

**`release_expired_hold()`'s dead-code gap (flagged as a real, open question in §3.10's own note above) is now closed, two ways.** Confirmed live: before this phase, an expired `HELD` reservation was never actually cleaned up by anything — `confirm_hold()` detected the expiry and raised, but never restored the slot's capacity, so an abandoned hold leaked its slot's capacity forever. Fixed: (1) `confirm_hold()` now calls the (also newly race-safe — see below) `release_expired_hold()` on expiry detection, recovering capacity the next time anyone touches that booking; (2) a real, genuinely-scheduled background sweep (`inventory_core.reconciliation.sweep_expired_holds()`, wired into a periodic loop in BPP's `core/reconciliation.py`, ticking every `RECONCILIATION_INTERVAL_SECONDS` — 60s by default) catches holds nobody ever touches again. Live-observed over this session's own testing: the sweep's very first tick after this deploy released **5 real abandoned `HELD` bookings** that had accumulated from earlier phases' own manual E2E testing — genuine cleanup, not a synthetic demo. A purpose-built short-TTL test hold, created and then deliberately abandoned (no confirm-touch, no manual release), was correctly detected and released at the sweep's very next tick after its TTL lapsed, restoring the slot to `AVAILABLE`/full capacity with zero manual intervention. The sweep also correctly paused while `bpp-backend` was killed for the scenarios below and resumed cleanly on restart — confirmed via its own log timestamps.

**Wiring two real concurrent callers into `release_expired_hold()` (the on-touch fix + the sweep) surfaced a genuine, previously-unreachable concurrency race** — see `livetracker2.md` §3.11 finding 2 for the full mechanism. Fixed by moving the status check under `select_for_update()`, same pattern as `confirm_hold`/`cancel_booking` already used. Verified with a real 8-thread concurrent test racing to release the same expired booking on a slot with real headroom below `capacity_total` (the case a naïve fix could still silently double-credit) — exactly one release wins, capacity restored exactly once.

**Kill BPP mid-`confirm`:** the customer-facing trigger call itself always returns `202` immediately — Gateway ACKs before it even attempts to reach BPP, so BPP being down never blocks or hangs the initial request. When BPP is actually unreachable, Gateway's `dispatch_confirm` retries for ~15s (DNS-resolution backoff) then gives up, logs, and returns silently (the same established fire-and-forget/log-don't-raise discipline used since `dispatch_select`/`dispatch_init`) — no NACK, no callback ever reaches BAP. Confirmed live: polling BAP's own `/api/v1/confirm/<transaction_id>` 20 times at 1.2s intervals (**exactly** the real frontend's own `usePoll` config, `BAP/web/app/confirm/page.tsx`) shows `confirmed_order`/`confirmed_error` staying `null`/`null` for the entire ~24s window — the backend genuinely never resolves this on its own. This is by design: the real frontend's own poll ceiling (`maxAttempts: 20`) is what turns backend silence into the customer-facing "Could not confirm this booking" clean error state, not a backend-side resolution — confirmed correct via direct code read of `usePoll.ts`/`confirm/page.tsx`, consistent with the identical pattern already relied on for `select`/`init`.

**Kill Redis (`bpp-cache`) — the failure mode was worse than just the TTL/reservation layer, confirmed live, now fixed.** Every BPP endpoint failed, not just booking/hold logic: `/search` itself returned a raw, unhandled `500 Internal Server Error` while `bpp-cache` was down, because BPP's own *inbound* trust-verification path (`trust.verify_bap_and_gateway` → `registry_client.lookup` → the Redis-backed circuit breaker's own `before_call()` state check) required Redis to even decide whether to attempt the real call — a dependency failure in the safety mechanism itself, not a graceful fallback. Confirmed via BPP's own traceback logs. Recovery was already automatic and immediate once Redis came back (no restart needed). Flagged in this phase as a follow-up (a `shared/resilient_http` change affecting all four apps, out of §3.11's own scope) and **fixed in the immediate follow-up**: `RedisCircuitBreaker.state`/`record_success`/`record_failure` (`shared/resilient_http/circuit_breaker.py`) now catch `redis.exceptions.RedisError` and fail open (report `CLOSED`) instead of letting the exception propagate — the real downstream call is still attempted and can fail with its own honest error, rather than a misleading circuit-breaker-internal crash. `redis` is imported lazily inside the affected methods, not at module level, since this module is imported unconditionally by every app including Registry, which has no `redis` dependency and only ever constructs the plain in-memory `CircuitBreaker`. Verified via a dead-Redis-client test double (no real outage needed to exercise the fix) plus full regression runs of all four apps' suites (Registry 47/47 — confirming the lazy import doesn't break its `redis`-less import path).

**Kill Redis, re-verified live again at Phase 3 Exit (2026-07-25) — the fail-open fix above stopped the `500`s, but a deeper, previously-invisible layer was still hanging real requests.** Re-testing `bpp-cache` down against `/search` showed BPP's own Daphne worker force-killing the request task ("took too long to shut down and was killed") after 10+ seconds, even with the circuit-breaker fail-open fix and `django_redis` exception handling (`rate_limit.py`/`metrics.py`/`catalog_cache.py`) already in place from earlier in this same exit pass. Root-caused through four successive rounds of live re-testing, each believed complete until disproved by the next real test:
1. `rate_limit.py`/`metrics.py`/`catalog_cache.py` had no Redis-outage exception handling at all — fixed, but only caught one exception type.
2. `cache.get()` raises `django_redis`'s `ConnectionInterrupted`; `cache.set()` was observed raising the raw `redis.exceptions.ConnectionError` instead — confirmed via `issubclass()` that these are unrelated exception classes. Both are now caught everywhere.
3. Neither fix helped without a socket-level timeout: no redis-py client anywhere had one configured, so a connect attempt against a stopped-but-present container could hang at the OS level for many seconds before any exception fired. Added `socket_connect_timeout`/`socket_timeout` to every redis-py client construction site (BAP/BPP/Gateway `registry_client.py`, BPP's `confirm_service.py`/`init_service.py`/`select_service.py`/`reconciliation.py`) and both Django apps' `CACHES` config.
4. Still not enough — a direct isolated test inside the container proved `socket_connect_timeout` only bounds the TCP-connect phase. DNS resolution against a stopped-but-not-removed container took **~4 seconds on its own** ("No address associated with hostname" / "Name or service not known"), a phase neither timeout kwarg touches at all. No redis-py/django-redis option bounds DNS.

**Fix: `shared/redis_safe/`** (restructured from a single throwaway file into a proper package with its own `tests.py`, matching this project's other `shared/` libraries) — a generic hard wall-clock deadline that runs a call off-thread and gives up waiting after a fixed timeout, regardless of which phase (DNS, connect, or I/O) is slow. Wired into every Redis touch point: `rate_limit.py`, `metrics.py`, `catalog_cache.py`, and `RedisCircuitBreaker`. Two more rounds of live testing were needed to land the implementation itself: a first version used a shared, fixed-size `ThreadPoolExecutor`, which silently dropped 2–3 of 800 real increments under BPP's own concurrency regression test — queuing delay for a free pool worker was counting against the same deadline meant to bound Redis, misclassifying a busy-but-healthy pool as an outage. Fixed by spawning a dedicated thread per call instead of sharing a bounded pool. The initial 0.5s deadline was then found to still be too tight under real thread-scheduling jitter at high concurrency on a local dev machine (2/800 dropped); raised to 2.0s, which passed cleanly there. Local full regression at that point: BPP 203/203 and BAP 165/165 with Redis healthy; live re-test with `bpp-cache` stopped showed real, correct catalog results returned (not empty, not crashed) with zero Daphne task-kill messages in the logs, at the cost of a few extra seconds of latency during the outage — the intended "slower, always correct" degradation, not a hang.

**Found again in CI, after opening the PR — the exact same failure signature, on a different environment, twice.** GitHub Actions' `Unit Tests (Python — BPP/backend)` job failed the same concurrency regression test at 2.0s (797/800) — CI runners are more resource-constrained/shared than the local dev machine that validated 2.0s, so the same real thread-scheduling jitter that forced 0.5s→2.0s locally recurred at 2.0s in CI's noisier environment. Raised to 5.0s — and CI still failed, this time `Unit Tests (Python — BAP/backend)`'s own **independent copy** of the same concurrency test (795/800), confirming this is a real, reproducible class of tail latency on CI's shared runners, not a one-off fluke. Raised again, to **10.0s**. Each dropped call was confirmed to be genuine scheduling tail-latency, not a logic bug: every `call_with_hard_timeout` invocation gets its own isolated queue and thread (no shared state between calls to race on), so a drop means that one call's dedicated thread genuinely didn't get scheduled/complete within the deadline on that run — realistic under a demanding 800-real-OS-thread-creation tight-loop burst (heavier than any actual traffic pattern) on a shared/throttled CI VM. 10.0s remains a small fraction of the original unbounded hang (10s+) this module exists to cap, and is irrelevant to normal (healthy-Redis) operation regardless of value, since a healthy call returns in microseconds either way. Lesson: this specific regression test's 800-call tight-loop burst is a genuinely more demanding concurrency stress pattern than typical CI-runner headroom accounts for — any future timeout tuning here must be re-verified in CI (both BAP's and BPP's copies), not just locally, before considering it settled.

**Correction (2026-07-26): the "tail latency" diagnosis above was wrong for at least one of these failures — a real logic bug, misdiagnosed as timing, hiding underneath it the whole time.** After PR #37 merged, the same BAP concurrency test failed a fourth time on a separate push-to-master CI run. Raising the timeout again (10.0s → 20.0s) not only failed to fix it — a local repro loop got *worse* (3 of 5 runs failed, dropping up to 10/800, versus the occasional 4-5/800 seen before). That inconsistency was the tell that timeout duration was never the actual variable. Root cause, found by reading `increment_counter()` (`shared/django_observability/metrics.py`) directly: `cache.incr()`, catch `ValueError` on a missing key, fall back to `cache.set(key, amount)` — a **non-atomic check-then-set**. The test's own `cache.clear()` fixture guarantees a brand-new key on every run, so multiple threads can genuinely race to discover "key missing" simultaneously and each independently `set()` it to their own single `amount`, silently overwriting each other and undercounting — a real bug present since this code was written, not a CI-runner scheduling artifact. `rate_limit.py` had the identical shape (found by grep once the pattern was known) and the identical bug. Fixed in both by replacing the fallback with `cache.add()` (django_redis's atomic "SET if not exists" — concurrent adds are safe, exactly one ever wins) called unconditionally *before* `cache.incr()`, removing the race window entirely rather than trying to win it faster. Verified with 10 consecutive local re-runs of the exact failing test (0 failures, previously ~3/5) plus a new dedicated 20-thread concurrency test for the rate limiter. The `call_with_hard_timeout` default was reverted back to 10.0s — the three prior escalations documented above remain genuine (each was independently confirmed as isolated per-call tail latency with no shared state to race on), but this fourth failure was never that class of problem, and 20.0s bought nothing. **Lesson:** when the same regression test fails again after a fix that was supposed to already cover it, re-derive the root cause from the code instead of assuming it's "more of the same" and reaching for the same lever (raise the timeout) a second time.

**Known limitation, not yet a real gap**: the dedicated-thread-per-call design has no ceiling on concurrent OS threads — fine at the concurrency levels tested here (up to 800 rapid calls, matching the existing regression test), but not load-tested past that point, and demonstrably sensitive to the underlying host's own scheduling headroom (see the CI finding above). If real traffic ever pushes concurrent Redis touches far higher, revisit this — e.g. a properly-sized bounded pool (large enough to avoid the queuing-misclassification bug this design was chosen to fix) or an async-native Redis client. No action needed at current pilot/dev scale.

**Registry outage, re-verified live under real `search` traffic (not just trust-layer plumbing) — still fails closed, still recovers automatically, and now shows a genuinely new chained-breaker behavior** since Gateway's own circuit breaker is on by default as of this phase (see below). Six sequential real search attempts through the full BAP→Gateway→Registry chain: ~24s, ~24s, ~12s, ~4s, ~4s, then ~0.4s — Gateway's own breaker (to Registry) tripped first, making Gateway itself start returning fast `500`s, which then also tripped BAP's *own* breaker (to Gateway) once enough of those accumulated. Full automatic recovery confirmed: the very next search after Registry restarted (past the 30s cooldown) succeeded in ~1.7s.

**Kill Gateway itself mid-`search` — the genuinely new scenario `livetracker1.md` Phase 4.2 explicitly left untested.** Confirmed live: every attempt returns a clean, honest, structured `SEARCH_UNAVAILABLE`/`retryable: true` error — never a hang, never a false success. First failures take ~20s each (BAP's own `resilient_http` client exhausting its retries against a DNS-unresolvable host). Real operational nuance found: because each slow failed attempt's own latency (~20s) is comparable to the circuit breaker's 30s reset cooldown, testing with slow, one-at-a-time sequential retries can miss the fast-fail window entirely — the breaker decays back to `HALF_OPEN` between attempts spaced that far apart, and each `HALF_OPEN` trial (since Gateway is still genuinely down) pays the full ~20s cost again before re-opening. Only confirmed the fast-fail path by sending 3 *concurrent* requests within the same open window — all three correctly fast-failed at ~1.4s. Full automatic recovery confirmed once Gateway restarted.

**Decision: Gateway's circuit breaker is now on by default.** `gateway-cache` promoted from the optional `with-gateway-cache` profile to an always-on `docker-compose.yml` service; `CACHE_ENABLED` now defaults to `true` in both `beckn-gateway/gateway/settings.py` and `.env`/`.env.example`. Reasoning: `search` (§3.1) put Gateway on continuous, customer-facing traffic for the first time — the old `[BETA]`-era default (opt-in, matching Gateway's earlier occasional-onboarding-traffic-only role) would otherwise mean every single request during a real Registry outage pays the full ~19s slow-fail path instead of the ~0.3s circuit-broken one. Now consistent with BAP's/BPP's own unconditional Redis dependency, not a special case.

**Reconciliation — catalog-cache sweep.** Live-tested per the Test Gate's exact wording: deliberately corrupted the cached `bpp:beauty_catalog` entry out-of-band, confirmed a reconciliation run detects and corrects it (covered by an automated test, `BPP/backend/core/test_catalog_cache.py`, exercising the same real `reconcile_beauty_catalog_cache()` the live scheduled loop calls). Minor honest caveat found live, now fixed: `build_beauty_catalog()`'s underlying queries had no explicit `.order_by()`, so consecutive builds could return the same data in a different list order — the scheduled sweep's own log line ("corrected a drifted/missing catalog cache entry") fired on nearly every 60s tick during that session even though nothing had actually changed. Harmless (the cache always ended up matching current reality either way) but a noisy signal for an operator trying to distinguish real drift from this ordering artifact. Flagged as a follow-up and **fixed in the immediate follow-up**: `BusinessAccount.objects.filter(is_active=True)` now has `.order_by("id")`, and each provider's own `Resource` query now has `.order_by("name", "id")` (a tie-break added on top of the pre-existing `"name"` ordering, for two resources sharing a name). Verified with a new regression test — three consecutive `build_beauty_catalog()` calls against unchanged, multi-business/multi-resource data now compare exactly equal.

**A third, independent bug found live and fixed in the same follow-up, unrelated to §3.11's own scenarios: a real thread-safety race in `participant_keys.py`'s lazy signing-key generation** (`BPP`/`BAP`/`beckn-gateway`, three independent copies). `functools.lru_cache` does not guarantee only one thread runs the wrapped function on a cache miss, and the old check-then-write body raced on `path.write_text()` (not atomic — open/truncate, write, close): a thread could read another thread's key file mid-write, raising `json.JSONDecodeError`. Surfaced as an intermittent failure in `BPP/backend/core/test_select.py`'s own real-concurrency test when run as part of the full suite (never in isolation) — the exact signature of a first-call race, not a logic bug in that test. A first attempted fix used double-checked locking with an unprotected fast-path read outside the lock; a dedicated new race-reproduction test (`test_participant_keys.py`, 25 concurrent threads against a fresh key path) caught that this still had the identical gap, just moved. Fixed properly by locking the entire function unconditionally — this function is called at most once per process in practice (`get_signing_keys`/`get_encryption_keys` are themselves `lru_cache`-wrapped), so there is no real hot path to optimize around. Verified stable across repeated full-suite reruns after the fix.
