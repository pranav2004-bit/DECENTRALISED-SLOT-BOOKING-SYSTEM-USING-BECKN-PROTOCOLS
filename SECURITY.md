# Security

## Reporting

If you find a security issue in this codebase, do not open a public issue. Report it privately to the project maintainer first.

## Threat Model Summary

This system's trust boundary is the Beckn/ONDC Registry (see [protocol_compliance_notes_v1.1.md](protocol_compliance_notes_v1.1.md) §A.5 — the Registry is a Public Key Infrastructure). The primary risks in scope for the foundation/trust-layer build ([livetracker1.md](livetracker1.md) Phase 0–4):

- **Participant impersonation** — mitigated by mandatory Ed25519 request signing on every endpoint (§C of protocol_compliance_notes_v1.1.md), verified against Registry-sourced public keys.
- **Private key compromise** — mitigated by never transmitting or logging private keys (§A.5), secrets-manager-only storage (below), and a documented rotation path (re-`/subscribe` with a new `key_pair`, per §B.4).
- **Registry/Gateway abuse** — mitigated by rate limiting at the real ONDC thresholds (Subscribe 10/min, Lookup 7,600/min — §B.6) and input validation on every API surface.
- **Replay attacks** — mitigated by time-bound, single-use on_subscribe challenges and `created`/`expires` bounds on every signed request.
- **Data exposure** — the Registry stores only minimum participant metadata (no catalogs/orders/payments — see [registry_details_v1.1.md](registry/registry_details_v1.1.md) §8); customer personal data handled by BAP/BPP is subject to DPDP Act obligations (protocol_compliance_notes_v1.1.md §E.4). **Transactional email (`livetracker3.md` §4.1):** `notifications.py` reads a customer's contact/booking details to compose confirm/cancel/reschedule emails, but `EMAIL_BACKEND` is Django's own file-based backend (writes to `BAP/backend/data/sent_emails/`) — no new external party sees customer data yet, so no new data-exposure surface exists today. Revisit this note the moment a real outbound provider (SMTP relay, SES, etc.) replaces the file backend — that will be a genuine new third party seeing customer contact info and belongs here when it happens, not before.

## Secrets & Key Management

**Strategy for `[MVP]`/`[PILOT]`:** secrets (Django secret keys, database credentials, signing/encryption private keys, payment gateway API keys) are injected via environment variables sourced from the deployment platform's secrets store (e.g., Docker secrets locally, a managed secrets manager in Dev/Staging/Prod). They are **never** committed to source control and never inlined in `.env.example` — only placeholder values live there.

**Deferred to `[ENT]`:** HSM/KMS-backed key custody for signing/encryption private keys. Evaluated but not required at foundation stage; revisit when transaction volume or compliance requirements (see protocol_compliance_notes_v1.1.md §E) justify the added operational complexity.

**Local/dev key persistence (real gap found and closed at Phase 3 Exit, `livetracker2.md`, 2026-07-24):** Registry/Gateway/BAP/BPP's ephemeral, dev-mode-generated signing and encryption key files (`participant_keys.py`, `registry`'s equivalent) were never written to a persisted Docker volume — every `docker compose` container recreate silently wiped them, breaking that participant's already-established trust relationship with Registry and requiring a full re-onboarding pass, repeatedly hit live during this project's own development. `docker-compose.yml` now mounts a named volume (`registry-secrets`/`gateway-secrets`/`bap-secrets`/`bpp-secrets`) at each service's key directory, so keys now survive an ordinary container recreate. This closes the local dev-experience data-loss problem only — it is **not** a substitute for the `[ENT]` HSM/KMS item above, and does not change this project's `[MVP]`/`[PILOT]` production-readiness status.

**Key rotation policy:** manual at `[MVP]` — re-run the Subscribe flow with a new `key_pair` before the current one's `valid_until` expires (protocol_compliance_notes_v1.1.md §B.4). No dedicated rotation endpoint exists in the protocol; this is the confirmed mechanism, not a placeholder.

**Enforcement:** a pre-commit secrets-scanning hook ([.pre-commit-config.yaml](.pre-commit-config.yaml), using `detect-secrets`) blocks commits containing anything that looks like a real key, token, or credential. This runs locally via pre-commit and again in CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) as a non-bypassable gate.

## Signing

Every inter-participant request is signed — see [protocol_compliance_notes_v1.1.md](protocol_compliance_notes_v1.1.md) §C for the exact `Authorization`/`X-Gateway-Authorization` header format, Ed25519 algorithm, and BLAKE-512 digest scheme. No endpoint (including `/lookup`) is unauthenticated.

## Dependency & Container Scanning

CI runs SCA (dependency vulnerability scan: `pip-audit`/`npm audit`), SAST (`bandit`, static analysis of every app's Python code), and container image scanning on every PR — see [.github/workflows/ci.yml](.github/workflows/ci.yml). Findings block merge unless explicitly accepted with a documented reason. Re-run in full across all Phase 1–4 business-layer code at `livetracker2.md` §4.7 Production Readiness Review, not just the trust-layer code it originally covered.

## Business-Layer Security Controls (livetracker2.md §3.7, now cross-domain: Beauty/Healthcare/Automotive)

The threat model above covers the trust layer (participant-to-participant, Registry-anchored). The booking workflow adds a second, distinct boundary: one customer of the same BAP against another. These controls were built against Beauty (§3.7) but are domain-agnostic by construction — the same trigger/result endpoints, session/rate-limit/CSRF machinery, and IDOR check apply unchanged to Healthcare (§4.1) and Automotive (§4.2), including Automotive's own multi-resource group operations (`find_group_bookings()`/`find_paired_resource()`, confirmed to introduce no additional IDOR surface — see `livetracker2.md`'s Phase 4.2 Change Log entry). Controls, all live-verified (Phase 3 Exit re-verification, `livetracker2.md`):

- **Session-ownership / IDOR protection** — every `SearchSession`-scoped trigger/result flow (search, select, init, confirm, status, cancel, update, track, rating, support) resolves through a single choke point, `resolve_owned_session()` (`BAP/backend/core/session_authz.py`): 404 for a nonexistent transaction, 401 if the session has an owner and the caller isn't authenticated, 403 if authenticated as a *different* customer, unrestricted for a still-anonymous session (matching this project's anonymous-browse UX), otherwise the owner. Deliberately distinct from the wire-layer `holder_ref` check at BPP (§3.3–§3.5), which protects against a wrong/malicious *BAP*, not a wrong *customer* of the same BAP.
- **Staff-login IDOR boundary** (`livetracker2.md` §4.3, BPP-side) — a `Resource` is owned by a business account (`owner_ref`); a staff account (`role=STAFF`, `managed_by=<owner>`) only ever has access to the one `Resource` its owner explicitly assigned to it (`Resource.domain_data["assigned_staff_id"]`, set by the owner-only `resource_assign_staff_view`). `_resource_accessible_to()` (`BPP/backend/core/views.py`) is the single shared check both entry points use: REST endpoints (`resource_availability_create`/`resource_availability_block`/etc.) return `404` (not `403`) on mismatch, same "can't distinguish not-yours-from-doesn't-exist" posture as the BAP session check above; the live-dashboard WebSocket (`ResourceAvailabilityConsumer`, §4.4) enforces the identical check at `connect()` time, closing with `4401` (unauthenticated) or `4403` (wrong owner/staff) before the socket ever joins the resource's broadcast group — and, since `livetracker3.md` §8.1's own fourth and fifth post-close audits (a real gap made concretely exploitable by that phase's new staff-unassign feature), re-enforces it again on both sides of a still-open connection too: on every inbound `block_slot` message (fourth audit) and before forwarding every outbound `slot_update` broadcast (fifth audit), closing with `4403` if access was revoked after `connect()` either way — a connection that outlives its own authorization can neither act on the resource nor keep watching it.
- **Rate limiting** — Redis-backed, per-endpoint (`django_observability/rate_limit.py`), returns `429 {"error": {"code": "RATE_LIMITED", ...}}` (API_CONVENTIONS.md shape). Currently applied to 13 BAP endpoints (signup/login at 5/min; search/bookings at 20/min; select/init/confirm/status/cancel/update/track/rating/support at 10/min) and 12 BPP endpoints (business-signup/business-login at 5/min, per-IP; staff/locations at 20/min; resource-create/resource-availability-create/resource-assign-staff/resource-availability-block/staff-status at 30/min — all seven keyed per authenticated business account rather than by IP; staff-password-reset at 10/min, also keyed per authenticated business account, the tighter tier matching signup/login as the closest precedent for a credential-setting action; bpp-rating/bpp-support at 30/min, per-IP since these are Gateway-forwarded wire callbacks, not an authenticated business session). `bookings` at 20/min (`livetracker3.md` §9.1, the real customer booking-history list, kept unauthenticated-IP-keyed like every other BAP endpoint since BAP has no per-account keying convention) is the newest addition to this count.
- **Reservation-hold abuse cap** — `MAX_CONCURRENT_HOLDS = 3` (`BAP/backend/core/select_service.py`): blocks a customer from opening more than 3 concurrent unconfirmed holds, closing a real capacity-DoS vector (holding slots indefinitely without confirming, starving other customers).
- **CSRF** — `signup`/`login` (both BAP and BPP) require a real Django CSRF token; the transaction trigger/result endpoints (search/select/.../track) stay `@csrf_exempt` since they're same-origin JSON APIs authenticated by session cookie + the ownership check above, not browser form submission. `SESSION_COOKIE_SECURE`/`CSRF_COOKIE_SECURE` are `True` outside `DEBUG`.
- **Input validation** — length caps on free-text fields (name/contact/query/domain, 255/500/100 chars) rejected with `400 VALIDATION_ERROR` before reaching the DB, avoiding an uncaught `DataError` surfacing as a raw 500.

## Compliance

This project is a private, self-contained Beckn network (see [livetracker1.md](livetracker1.md)'s scope declaration) and does not pursue real-ONDC certification. [protocol_compliance_notes_v1.1.md](protocol_compliance_notes_v1.1.md) §E documents the full real-ONDC compliance/certification layer (Pramaan certification, ONDC Network Participant Agreement, IGM/GRO designation) as reference facts about the real network only — these are marked `[N/A]` in [livetracker1.md](livetracker1.md) Phase 4.4 and would only become relevant if real ONDC integration is pursued later. DPDP Act obligations around customer personal data are the one item in that checklist kept as general good practice, independent of ONDC.
