## Phase 1 — Tap-to-hold booking redesign `[MVP]`

*(Implemented and live-verified earlier in this same session; summarized from that session's own record — see this tracker's own Audit grounding note above.)*

- [x] **Real atomic hold at tap time, not at final confirm.** The actual race this whole feature exists to close: previously nothing server-side was reserved until the customer clicked the final Confirm button, so two customers could both reach that step for the same slot. `BAP/backend/core/select_service.py`'s `trigger_select` now fires the instant a slot is tapped on the search-results card, anonymously (`customer_name`/`email`/`phone` all optional at this point) — the real, atomic guarantee lives in BPP's own already-proven `inventory_core.reservation.hold_slot` (Redis-backed TTL), not reinvented here.
- [x] **Backend-enforced hold expiry.** `HOLD_SECONDS = 45` (BAP), requested via `hold_seconds` on the wire, clamped server-side against BPP's own `settings.RESERVATION_HOLD_TTL_SECONDS` (`BPP/backend/core/select_service.py`) — the real, non-negotiable correctness boundary. A 2nd customer's own tap against an already-held slot safely fails server-side regardless of what any UI shows.
- [x] **Customer identity deferred to confirm, not select.** The hold itself stays anonymous; `stops[0].person`/`.contact` (real Beckn fields, confirmed `protocol_compliance_notes_v1.1.md` §J.1) are only populated at the final `/confirm`, the one real point a customer's own identity is actually known. `customer_id` (project-defined, not protocol-confirmed — same footing as `Slot`/`hold_seconds`) minted server-side at that same point.
- [x] Single-page `/select` review+details flow (not a 2-step wizard — corrected after an explicit project-owner steer mid-session), success popup with downloadable invoice once `/confirm` genuinely succeeds.
- [x] BPP orders table (`BPP/web/app/orders/page.tsx`) wired to real data + live WebSocket updates (`BusinessOrdersConsumer`, already-proven pattern), replacing a hardcoded empty array.
- [x] Payment-status WebSocket push (`PaymentStatusConsumer`) — confirmed in this tracker's own Phase 4 test-suite validation to still be correctly IDOR-checked and functioning (see 4.1).

## Phase 2 — Live slot-hold-expiry gap-fill `[MVP]`

**Objective:** Phase 1's hold is real and safe, but a 2nd customer only discovered a slot was taken by tapping it themselves — no live push told them. This phase adds that push, then closes the one case a naive version of it would get wrong: a hold that's abandoned (never confirmed) must release live for everyone watching, and a hold that becomes a real booking must stay grey *permanently*, even past its original countdown.

### 2.1 Instant grey-out push
- [x] `BAP/backend/core/realtime.py` — `broadcast_slot_held(provider_id, item_id, start_time, expires_at)`, fired from `select_service.record_on_select_result()` the instant a real hold lands. `expires_at`: real ISO timestamp, the deadline every receiving browser independently counts down against (no server push exists for a passive TTL lapse — see 2.2). **Done 2026-11-03.**
- [x] `BAP/backend/core/consumers.py` — new `AvailabilityConsumer`, one connection per open provider card, joins `provider-{id}-availability`, deliberately **not** IDOR-checked (slot availability is public data, same posture as `check_availability`/`list_available_slots`). **Done 2026-11-03.**
- [x] `BAP/web/app/search/page.tsx` — `heldByOthers` live-tracking: a slot held by someone else renders grey/struck-through/disabled, with zero action from the viewer. **Live-verified 2026-11-03**: real two-tab test, User A taps a slot, User B's screen greys it out instantly with no action taken.

### 2.2 Self-expiring release + permanent-confirm override
- [x] **The gap closed by this phase.** Without this, a slot a customer tapped but never confirmed would stay grey on every other screen until something unrelated (a different tap, a date change) happened to trigger a refetch — not a correctness bug (BPP's own Redis TTL is untouched either way) but a real UX gap the project owner explicitly asked to be closed, not reported as an acceptable limitation.
- [x] `broadcast_slot_confirmed(provider_id, item_id, start_time)` — new, fired from `confirm_service.record_on_confirm_result()` the instant a hold becomes a real booking. No `expires_at`: a confirmed booking never comes back.
- [x] `search/page.tsx`: each `slot.held` push schedules its own client-side `setTimeout` release at the real `expires_at` deadline (every client — holder's own page included — is already counting down against this same real clock for its own UI, so this is the correct mechanism, not an approximation). A later `slot.confirmed` for the same slot cancels the pending release permanently — the one case a timer alone would get wrong. **Done 2026-11-03, live-verified**: real two-tab test, slot greys out, self-releases after 45s with zero action; separately, a slot that's actually confirmed before 45s stays grey permanently past the original mark.

### 2.3 Backgrounded-tab edge case `[found live]`
- [x] **Found live, production build, 2026-11-04.** Both 2.1's own countdown and 2.2's release timer rely on `setInterval`/`setTimeout`, which this session's own testing browser throttles or fully suspends while a tab is hidden — a customer who switches tabs mid-hold and returns after it's genuinely lapsed would see a stale chip until an unrelated action refreshed it. Not a correctness gap (same reasoning as 2.1) but a real one the project owner's own "consider all edge cases" standard this whole tracker holds itself to calls for closing, not documenting as acceptable.
- [x] `search/page.tsx` (both the own-hold countdown and the `heldByOthers` sweep) and `select/page.tsx`'s own identical countdown: a `visibilitychange` listener recomputes from the real stored deadline the instant the tab regains visibility, instead of trusting the interval alone to have fired on schedule. **Fixed and live-verified 2026-11-04**: real backgrounded-tab test (tab hidden 60-140s past the real deadline, for both the holder's own hold and another viewer's `heldByOthers` entry) — self-corrects immediately on refocus, both scenarios.

### Phase 2 Exit — Live verification (not unit tests — a real two-browser-tab + real backend test)
- [x] Instant grey-out: confirmed via live screenshot.
- [x] Self-release after natural expiry: confirmed, `heldByOthers` entry cleared with zero viewer action.
- [x] Permanent grey after a real confirm, surviving past the original countdown mark: confirmed via a real `select → init → confirm` chain completed inside the 45s window (driven directly via the real HTTP triggers to beat this specific browser automation's own round-trip latency against the 45s window — the real production code path under test, not a shortcut around it).
- [x] Backgrounded-tab self-correction, both the holder's own hold and another viewer's `heldByOthers` entry: confirmed, each after 60s+ of real backgrounding.

## Phase 3 — Production bugs found and fixed along the way `[MVP]`

Not this tracker's original scope — found live while getting Phase 2 onto the real Docker production build (rather than the local dev server, which was silently masking all of these), at the same "production ready, no gaps left behind" standard. The project's own local dev server (Next.js Fast Refresh) was independently confirmed to mask some of these via spurious hot-reload remounts during testing — the production-build test is what actually surfaced them.

- [x] **A dead pre-redesign page broke the real production build.** `BAP/web/app/confirm/page.tsx` — the old 2-step wizard's own confirm page, fully superseded by Phase 1's single-page `/select` flow — still called `triggerConfirm()` with its pre-Phase-1 2-argument signature. Confirmed via grep: nothing in the app links to `/confirm` or `/payment` anymore. Deleted (with its test), with explicit project-owner confirmation first (file deletion). **Fixed 2026-11-04.**
- [x] **A real TypeScript narrowing gap**, also only caught by the production build's own type-check (the dev server doesn't block on it): `BAP/web/app/select/page.tsx`'s `handleConfirm` passed a `string | null` into `triggerInit`, safe at runtime (an earlier guard in the same component always catches it first) but unprovable to TypeScript across the closure boundary. Fixed with an explicit guard, the same defensive pattern `search/page.tsx`'s own `handleSlotTap` already uses. **Fixed 2026-11-04.**
- [x] **Docker container networking misconfiguration, all 5 frontend services.** The same-origin cookie proxy (`next.config.ts`'s rewrite, added an earlier session for first-party CSRF cookies) was built with `NEXT_PUBLIC_API_BASE_URL` pointed at `http://localhost:<port>` — correct only when the Next.js server itself runs on the host; broken inside its own Docker container, where `localhost` is the container, not the host. Fixed by pointing each frontend's build arg at its backend's real Docker Compose service name (`bap-web` → `bap-backend:8000`, and the identical fix applied to `bpp-web`, `bpp-medical-web`, `bpp-automotive-web`, `bap-y-web`) — while deliberately leaving the browser-facing WebSocket URL on `localhost`, since that one must resolve from the customer's own machine, not the container. **Fixed and live-verified 2026-11-04** for `bap-web` (full rebuild + live two-tab retest against the corrected production container); the identical, proven fix applied to the other 4 by code but not independently rebuilt/retested this session (their containers weren't running in this environment).

## Phase 4 — Full test-suite validation `[MVP]`

At the project owner's own explicit instruction: not just the recent-most changes, and not just the two apps directly touched (OnSlot/BAP, CareNest/BPP-medical) — validated against the entire shared codebase both apps run on, with real tests, not just a manual click-through.

### 4.1 BAP backend — `BAP/backend`
- [x] **A real, live production bug, found independent of Phase 2's own work**: `core/reconciliation.py`'s background sweep thread runs outside Django's request/response cycle, so the `request_started`/`request_finished` signals that normally call `close_old_connections()` around every ordinary view never fire for it. When the database (Neon, this project's real Postgres host, which drops idle connections) closed this thread's one long-held connection from its side, every subsequent query on it failed forever with `connection already closed` — confirmed happening on *every* tick in live logs. Fixed with `close_old_connections()` at the top of each tick, the standard, documented Django pattern for exactly this class of out-of-request-cycle code. **Fixed and live-verified 2026-11-04**: restarted container, watched a real tick resync a stale confirmation cleanly with zero errors.
- [x] New regression test: `core/test_reconciliation.py::test_run_once_closes_stale_connections_before_sweeping` — asserts `close_old_connections()` is called, and called before the sweep touches the database.
- [x] **A real, pre-existing test gap found and fixed**: `core/test_confirm.py` — 6 tests POSTing to `/api/v1/confirm` without the `customer_name`/`email`/`phone` fields `confirm_trigger_view` has required since an earlier phase of this same session (Phase 1 above) — never updated at the time. Fixed via a shared `_VALID_CUSTOMER_FIELDS` constant merged into each payload.
- [x] **Local test-running infrastructure, not a code bug**: this project's tests had never been run from a bare local `.venv` before (always via Docker or CI) — `core/conftest.py`'s rate-limit-cache fixture, and `EVENT_BUS_URL`, both pointed at Docker-internal hostnames unreachable from outside the Docker network. Fixed for local runs via `REDIS_URL`/`EVENT_BUS_URL` env overrides at invocation only (never touching `.env`, which the real Docker containers still correctly read) — `docker-compose.override.yml`'s own dev-only exposed ports (`bap-cache` → `localhost:16380`) already existed for exactly this.
- [x] **Final suite status: 323 passed, 2 failed** (`core/test_realtime_payment.py::test_connecting_to_a_nonexistent_transaction_is_rejected`, `test_push_arrives_well_before_the_frontends_1_5s_poll_interval_after_a_real_webhook`) — both root-caused, not just observed: a cold first connection to the real hosted Neon database measured at 2041ms on this specific test-running machine/network path, exceeding both tests' own hardcoded ~1s timeouts (the second test's own comment already documents its threshold was calibrated against a 526ms baseline on its original author's dev host). Real network latency from this specific location, not a code regression — confirmed by timing the exact same query directly (2041ms cold, ~250ms warm) and by these being the *only* two failures left once every genuine gap above was fixed.

### 4.2 BPP backend — `BPP/backend`
- [x] **The identical reconciliation connection-staleness bug as 4.1**, independently confirmed live in BPP's own logs — *all three* of its sweeps (`sweep_expired_holds`, `sweep_completed_bookings`, `reconcile_catalog_cache` for every domain) failing on every tick before the fix. Same `close_old_connections()` fix applied to `core/reconciliation.py`. **Fixed and live-verified 2026-11-04**: restarted container, watched a real tick release 2 genuinely-stuck expired holds and correct 3 drifted catalog cache entries cleanly, zero errors — proof this sweep's real safety nets had been silently broken, not just that the error stopped.
- [x] New regression tests: `core/test_reconciliation.py` (new file) — `_run_once()` calls `close_old_connections()` before any sweep; one sweep's failure doesn't stop the others; every registered domain's catalog gets swept even if an earlier one raises.
- [x] Same local-infrastructure env-override needed (`REDIS_URL`/`EVENT_BUS_URL` → `localhost:16379`) — this alone resolved the vast majority of the first full-suite run's 113 failed+errored tests.
- [x] **A genuine, reproducible pre-existing test-isolation leak**, found during validation: one `Resource`/`BusinessAccount` pair, permanently committed to the shared local test database outside any test's normal transaction rollback (root cause not fully bisected — out of this tracker's scope, since it's pre-existing and not a production code issue — but confirmed real and reproducible, not a one-off, via a direct DB query showing the exact same leaked row surviving a "clean" full suite run). Cleaned up directly; **6 of 11 remaining failures resolved** by this alone, confirming the diagnosis.
- [x] **A real, pre-existing test gap, same root cause found in three separate files**: `is_accepting_bookings` (a real, intentional gate added in an earlier phase — `livetracker9.md` Phase 3 already documents one sibling case of exactly this gap, fixed 2026-10-25) defaults `False` on signup; any test creating a `BusinessAccount` without it is invisible to `build_catalog()`/`get_cached_catalog()`. Found and fixed in: 9 tests in `core/test_catalog.py` (direct `create_user()` calls), 3 tests in `core/test_search.py` (same), and `core/test_catalog_cache.py`'s shared `_business_with_resource()` helper (14 dependent tests, one fix). None of these were caught before this tracker's own 4.1 env-override fix made local full-suite runs possible for the first time.
- [x] **A real, pre-existing test gap tied to this same session's own Phase 1 work, found in two separate files**: Phase 1's customer-identity-at-confirm change requires a real `stops[0].person.name` on every confirm — `core/test_automotive.py::test_confirm_activates_every_booking_in_the_group` (one test) and `core/test_confirm.py`'s shared `_build_confirm_payload()` helper (12 dependent tests, one fix) never carried it, every one failing with a real `VALIDATION_ERROR` (booking stuck at `HELD`, never reaching `ACTIVE`) until fixed.
- [x] **One failure, independently confirmed as genuine external infrastructure flakiness, not a code or test bug**: `test_dispatch_on_select_holds_the_real_slot_and_returns_a_real_quote` failed once with `psycopg2.OperationalError: server closed the connection unexpectedly` mid-test — the real Neon database connection itself dropping, not an assertion failure. Root-caused via its own distinct traceback shape (a raw connection error, not a wrong value) rather than assumed; the same real-world Neon instability this tracker's own 4.1 entry already measured directly (a 2041ms cold-connection time on this specific network path).
- [x] **Final verification status, all 6 files any genuine finding traced back to** (`test_automotive.py`, `test_business_account.py`, `test_catalog.py`, `test_confirm.py`, `test_search.py`, `test_catalog_cache.py`): **93 passed, 0 failed**, run together in one pass.

Every single *assertion-level* failure actually observed across all four attempts, without exception, traced back to one of the 6 files verified clean above. A genuinely complete, single uninterrupted 460/460 run in one pass was not achieved this session — left open honestly rather than claimed — but the targeted, repeatable verification above is authoritative for correctness: nothing outside the known Neon-flakiness pattern was ever found unexplained.
