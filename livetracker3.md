1. Work phases **top to bottom** where a real dependency exists (§2's rating aggregation must exist before §3.1's rating-submission UI can show a meaningful confirmation; §7's signup form must reuse §6's own domain-list decision rather than making a second, independent, possibly-drifting one, per §7.1's own explicit callout; §8's staff-management screen and login flow explicitly reuse §7's dashboard-home and `/login` page rather than building parallel ones, per §8.1's own callout; §9's booking-history list reuses BAP's own already-existing `/account` login, not a new dependency on any other newly-found phase; §10 has no dependency on any other phase either — a self-contained backend bug fix, found while auditing §9 but not required by it), but unlike `livetracker1.md`/`livetracker2.md` this tracker is **not** one continuous vertical slice — §1 (search), §2–3 (rating/support/track), §4 (notifications), §5 (docs/testing), §6 (customer-facing domain selection), §7 (business-facing signup/login), §8 (staff-management UI), §9 (customer booking-history UI), and §10 (cancellation re-attempt data integrity) are nine genuinely independent gap-closure efforts found across two separate audits (the original 23-finding one, and five live findings surfaced mid-work), not sequential building blocks of one feature, **except** §6→§7 and §7→§8's explicit dependencies noted above. Work everything else in any order that suits real priority; the numbering here reflects the order each gap was surfaced in, not a mandatory build order.
2. A task/subtask is checked `[x]` **only** after its implementation is complete **and** its Testing & Validation Gate passes. Never check a box on implementation alone.
3. A phase is closed **only** after its "Phase Exit — Testing & Sign-off" section is fully checked.
4. If implementation reveals a decision not captured in a component's `*_details.md`, update that file in the same work session with an additive "Implementation note" callout — never rewrite the original client-provided content, and never touch `project_details.md`. Also update whichever root-level doc (`SECURITY.md`, `API_CONVENTIONS.md`, `OBSERVABILITY.md`, `TESTING.md`) the change actually affects.
5. Lifecycle tags on each item show when it's required. §4 (Notifications) is deliberately tagged `[BETA]`, not `[MVP]` — the project owner explicitly confirmed email/SMS delivery is optional, not a blocking gap, during the audit that produced this tracker (see Change Log). Do not build it ahead of its tag; do not skip a tagged item at its own stage.
6. Every finding this tracker closes was reached by **directly reading the running code**, not by re-deriving from documentation — three of the six areas below (§1, §2, §3) were only discovered because a summary-level assumption ("search filters results," "ratings are shown somewhere") turned out to be false on inspection. Any new task discovered while working this tracker should be verified the same way — against the actual code — before being marked a real gap.
7. When a shared module changes after `livetracker2.md`'s business flows already depend on it (e.g. `catalog.py`'s query-filtering logic, touched by §1), re-run the affected downstream test gates from `livetracker2.md` (specifically §3.1/§3.8's search and cache tests) before considering the change safe — the same "prove the whole chain again" discipline used throughout both prior trackers.

## Phase 1 — Search Correctness (closes Finding #21)

**Objective:** Make `/search` actually filter by what a customer typed. The audit's most severe finding in this tracker: `BAP/backend/core/search_service.py`'s `trigger_search()` correctly places the real query text on the wire (`message.intent.item.descriptor.name`), but `BPP/backend/core/search_service.py`'s `dispatch_on_search()` never reads `payload["message"]["intent"]` at all — it calls `get_cached_catalog(context["domain"])` and returns the entire domain's catalog unfiltered, every time, regardless of what was typed. Confirmed 0/100 on actual query relevance, not a "basic vs. sophisticated" quality question.

### 1.1 Query-Text Filtering in BPP's Catalog Build `[MVP]` — **CLOSED 2026-07-29**
- [x] `dispatch_on_search()` reads `message.intent.item.descriptor.name` (and, if present, `message.intent.category.descriptor.code`/`message.intent.fulfillment.type`) from the real inbound payload, not just `context["domain"]`. **Implementation note:** only `item.descriptor.name` is actually read — a direct re-check of `BAP/backend/core/search_service.py::trigger_search()` (the only place BAP builds an outbound intent) confirmed it never populates `category.descriptor.code` or `fulfillment.type` anywhere today, so there is nothing real to filter on for those two fields yet; wiring them now would be inventing a code path with no caller, the same "no invented sophistication ahead of real need" discipline this section's own §1.1.2 bullet already applies to ranking. Add real handling for those fields if/when BAP's own intent-building ever actually sets them.
- [x] `build_catalog()`/`build_beauty_catalog()` (and the Healthcare/Automotive equivalents) gain a real filter step: resources whose `descriptor.name` (and their owning `BusinessAccount`'s descriptor) don't match the query text are excluded from the returned catalog — **word-tokenized, case-insensitive AND-match** (split the query into words, match if every word appears as a substring somewhere in the combined searchable text), not a single literal substring match on the whole query string. A pure literal-substring match would leave a real, common failure mode unfixed: a query like "hair salon" would never match a resource/business descriptor of "Salon Hair Care" (same words, different order) even though that's exactly the kind of real query this fix exists to serve. This is not fuzzy/typo-tolerant matching (still explicitly out of scope, §1.2) — it's the minimum needed for "search actually reflects what was typed" to be true for realistic multi-word queries, matching this project's already-established "no invented sophistication ahead of real need" discipline (§3.8 of `livetracker2.md` set this same bar for caching) without under-shooting the actual, common case. **Implementation note:** `build_catalog()`/`_business_to_provider`/`_resource_to_item` (unified single domain-parameterized function since §4.1 — there are no longer separate `build_beauty_catalog()`/Healthcare/Automotive function bodies) are left untouched; the filter is a new, separate `filter_catalog(catalog, query_text)` in `BPP/backend/core/catalog.py`, applied by the caller after the catalog is built/read — see the next bullet for why this placement, not a `build_catalog()` change, is the correct fix.
- [x] An empty/missing `intent.item.descriptor.name` (a customer browsing without typing anything) falls back to the existing unfiltered full-domain-catalog behavior — not a regression, a defined behavior for the "browse everything" case, which is a real, legitimate use of `/search`
- [x] `get_cached_catalog()`'s existing cache key (§3.8 of `livetracker2.md`, currently keyed on domain only) is re-examined: caching per-query-text would explode cache cardinality for a low, real hit-rate benefit, so the correct fix is caching the **unfiltered** per-domain catalog as today (unchanged) and applying the new query filter **after** the cache read, on the (already fast, in-memory) result — not a cache-design change, a filter-placement decision, recorded here explicitly rather than left for whoever implements it to guess
- **Test Gate:** `FUNC`/`NEG`/`REGR` — a real search for "Priya" (an existing seeded stylist's descriptor name) returns only resources matching that text, not the full catalog; a search for a nonsense string returns zero results, not an error; an empty query still returns the full domain catalog (unchanged prior behavior); `livetracker2.md` §3.1's existing search E2E test and §3.8's cache-hit/invalidation tests are re-run and still pass, proving this change didn't regress the already-proven cached-search path. **PASSED 2026-07-29** — real Docker container rebuild + `pytest` run (not mocked/simulated), `BPP/backend/core/test_catalog.py` (6 new `filter_catalog()` unit tests, including a real "Senior Stylist - Priya" match, a nonsense-query zero-result case, and the exact "hair salon"/"Salon Hair Care" word-order case named above) + `BPP/backend/core/test_search.py` (2 new `dispatch_on_search()` integration tests proving the real wire payload's query text narrows the real catalog sent to Gateway) all pass; full re-run of every pre-existing `test_search.py`/`test_catalog_cache.py`/`test_catalog.py` test (35/35) plus the entire BPP backend suite (285/285) confirms zero regression. **Live E2E confirmation, 2026-07-29 (beyond the tracker's own stated gate, done to close out any remaining doubt at Phase 1 sign-off):** a temporary second live business ("Priya Live-Check Salon" / "Priya Live-Check Special") was seeded alongside the stack's existing "E2E Salon 45" / "Stylist E2E-45", and two real searches were driven through the actual running Docker network via `BAP/web/app/search/page.tsx`'s own real backing endpoint (`POST /api/v1/search` on `bap-backend`, `curl`, not simulated) — `"Priya"` returned only the Priya salon/resource, `"Stylist E2E"` returned only the E2E salon/resource, each correctly excluding the other's real data end-to-end (BAP → Gateway → BPP `dispatch_on_search` → Gateway → BAP, matching the real signed/relayed path, not a shortcut). Also confirmed `filter_catalog()`'s output still validates against the real `beauty_catalog.schema.json` contract (unchanged shape, fewer entries). Test data cleaned up after verification. Also confirmed live: a real, already-built customer-facing search UI (`BAP/web/app/search/page.tsx`, a text `FormField` wired to `triggerSearch(trimmed, domain)`) already exists and sends the actual typed text as the real query — so this fix is genuinely reachable by an actual customer today, not backend-correct-but-practically-unreachable.

### 1.2 Basic Relevance Ranking (stretch, not required for this gap to close) `[BETA]` — **explicitly DEFERRED 2026-07-29**

- **Test Gate:** `SANITY` — with two matching resources of different average ratings, the higher-rated one is returned first; this bullet is optional and may be deferred without blocking Phase 1 Exit if the project owner deprioritizes it once §1.1 closes the actual severity-0 gap. **Deferred, not run** — no `average_rating` field exists to test against yet; revisit once Phase 2 §2.1 (rating aggregation) of this tracker is built, at which point this becomes a real, testable task rather than a stub.

## Phase 2 — Rating Lifecycle Completion (closes Finding #22)

**Objective:** Close the "stored but never surfaced" gap for ratings. `Rating` (built in `livetracker2.md` Phase 4.5) correctly receives, validates, and stores real `/rating` submissions — a direct grep for `average_rating|avg_rating|Avg(|rating_count|aggregate.*[Rr]ating` across `BPP/backend/core` and `shared/inventory_core` returned zero matches. A rating is saved and then never appears anywhere again: not in search results, not on a provider's profile, nowhere. The customer-facing value of having submitted one is currently zero.

### 2.1 Rating Aggregation `[MVP]` — **CLOSED 2026-07-29**
- [x] A real aggregation mechanism computing, per rated entity (keyed the same way `Rating.entity_id`/`rating_category` already resolves against a `Booking` per `livetracker2.md` §4.5's own design), an `average_rating` and `rating_count` — decide explicitly whether this is computed on write (incremental update at `/rating` submission time, matching this project's established "synchronous core, no invented async step" discipline for anything that isn't genuinely a scale problem yet) or via a periodic sweep (mirroring the existing `sweep_expired_holds()`/`sweep_completed_bookings()` pattern in `shared/inventory_core/reconciliation.py`) — the on-write approach is the honest default absent a real scale reason for the sweep approach, since rating submission volume is nowhere near what would make an inline aggregate update a real bottleneck. **Implementation:** on-write, chosen exactly as recorded above. `Resource` gains `average_rating` (nullable — an honest "no aggregate-eligible rating yet", never a fabricated `0.00`) and `rating_count`. `rating_service.py::_adjust_resource_rating_aggregate()` updates it inside `transaction.atomic()` with `select_for_update()` on the one `Resource` row being changed — the same real-concurrency discipline `hold_slot()` already uses, since `/rating` is a real, concurrently-reachable wire action, not a hypothetical race.
- [x] Aggregation is scoped correctly per `Rating.rating_category`: an `Order`/`Fulfillment`-category rating (the two categories this project's flow actually produces today, per §4.5's own resolution logic) rolls up to the `Resource`/`Provider` the underlying `Booking` belongs to — not conflated with `Item`/`Agent`/`Support`-category ratings, which this project's own rating submissions have never actually populated but which the schema still allows and the aggregation must not silently mis-bucket if one ever arrives. **Implementation:** `_AGGREGATE_ELIGIBLE_CATEGORIES = {Order, Fulfillment}` gates aggregation explicitly in `dispatch_on_rating()`; any other category is still recorded as a plain `Rating` row, never touches `Resource`.
- [x] **Security correction, found during this tracker's own final audit pass (2026-07-29) — the original draft of this bullet was wrong and would have shipped a reputation-manipulation hole.** A rating submitted against a booking the calling transaction doesn't own (the existing, already-correct IDOR handling from §4.5 — captured as real feedback, just not FK-linked) is **excluded from the public-facing `average_rating`/`rating_count`**, not counted in it as originally drafted. Reasoning: `rating_category`/`entity_id` on an unlinked submission are caller-supplied and unverified against any real booking — counting them toward the public number would let anyone submit unlimited ratings against any resource they name, with no requirement to have ever booked it, directly enabling review-bombing (tanking a competitor) or self-inflation (rating your own resource from a throwaway transaction). Only ratings that successfully FK-link to a real `Booking` the calling transaction genuinely owns are aggregate-eligible; unlinked submissions are still stored (existing §4.5 behavior, unchanged) for audit/investigation purposes only, never rolled into the number a customer sees. **Implementation:** `dispatch_on_rating()` only calls `_adjust_resource_rating_aggregate()` when `booking is not None` (the existing `holder_ref` ownership check, unchanged) — an IDOR-mismatched submission takes the same `Rating.objects.create()` path it always did, `booking=None`, never touching `Resource`.
- [x] **Duplicate-submission handling, not addressed in the original draft.** One rating per `(Booking, rating_category)` from its true owning transaction: a second `/rating` call against the same already-rated booking updates the existing `Rating` row in place (the honest, real-world-correct behavior — "I meant to give 5 stars, not 3" is a legitimate correction, not abuse) rather than being silently rejected or double-counted in the aggregate. A DB-level uniqueness constraint on `(booking, rating_category)` enforces this is never violated even under a race (two near-simultaneous submissions for the same booking). **Implementation:** `Rating.Meta.constraints` gains `UniqueConstraint(fields=["booking","rating_category"], condition=Q(booking__isnull=False))` (migration `0009`, scoped to FK-linked rows only — unlinked submissions share no real identity to dedupe against).
  **Correction found and fixed (2026-07-29, same day, via the project owner's own explicit "any gaps left behind?" re-verification request after this section was first marked closed):** the first implementation used `update_or_create()` with a *separately pre-fetched* "old value" read before the call — race-safe against the DB constraint (no duplicate row could ever exist) but **not** race-safe for the aggregate *math*: under a genuinely concurrent double-submission (a real, plausible case — a double-click, a client retry, not just an adversarial scenario), the losing thread's stale pre-fetch made it treat a real update as a new rating. **Empirically confirmed live before the fix:** two concurrent submissions ("2","5") against one booking left exactly 1 `Rating` row (constraint held) but `rating_count == 2` and `average_rating == 3.50` — the aggregate silently drifted from reality even though the row-level guarantee was intact. **Fixed:** `dispatch_on_rating()` now wraps the read-old/write-new step in one `transaction.atomic()` block using `select_for_update().get_or_create()` to lock the one real `Rating` row (existing or newly-contended) before reading its prior value, so no thread can act on a stale read. **Re-verified after the fix:** a new automated concurrency test (`test_dispatch_on_rating_concurrent_resubmission_never_overcounts`, using real threads per this project's own established `test_rate_limit_counts_every_request_under_real_concurrent_traffic` pattern) plus 5 repeated live runs against the actual running container — all confirm exactly 1 row, `rating_count == 1`, and a correct last-write-wins average every time. Recorded here rather than silently rewritten into the original bullet, matching this tracker's own "corrections are new entries, never silently rewritten history" discipline.
- [x] **Rate-limiting coverage gap, found during this tracker's own final audit pass — must be verified, not assumed either way.** `livetracker2.md` §3.7 built Redis-backed rate limiting for the original 8 wire actions; `/rating`/`/support` were built later, in Phase 4.5, after §3.7's own endpoint list was written. Confirm directly (grep `rating_service.py`/`support_service.py` for the existing rate-limit decorator) whether that coverage was ever actually extended to these two endpoints. If not — a real, live gap, not a hypothetical — extend the same mechanism to both before this phase closes; without it, the abuse vector the bullet above just closed by construction (aggregate-eligibility) is still reachable as a pure volume/DoS problem against the unlinked-but-stored feedback table, and `/support` remains unprotected against simple spam. **Confirmed real, live gap:** neither `rating_view` nor `support_view` (BPP `views.py`) carried `@rate_limit` — consistent with none of BPP's other 6 wire-receiving views having it either (a wider, pre-existing pattern out of this bullet's scope), but still a real, closeable gap for these two. **Fixed:** both now carry `@rate_limit(limit_per_minute=30, scope="bpp-rating"/"bpp-support")` — a generous defense-in-depth ceiling (BAP's own customer-facing `rating_trigger_view`/`support_trigger_view` already had `@rate_limit(limit_per_minute=10, ...)`, confirmed still in place; this is a second, IP-keyed layer protecting BPP itself from being flooded regardless of origin BAP).
- [x] **Input-validation gap, found on this tracker's own second audit pass — the aggregation design as drafted assumed a data shape the real schema doesn't guarantee.** `protocol_compliance_notes_v1.1.md` §O already confirms `Rating.value` is deliberately a free-form string, since the real `Rating.yaml` schema allows it to carry a bare number *or* a comparison/logical expression (`gt`/`gte`/`&&`). ## Phase 10 — Cancellation Re-Attempt Data Integrity (new finding, found 2026-07-30, while auditing Phase 9)

**Objective:** A real, confirmed backend bug, not a UI gap like Phases 6-9 — found while verifying Phase 9's own status-derivation logic rather than trusting it. `trigger_cancel()` (`BAP/backend/core/cancel_service.py:66`) unconditionally resets `session.cancelled_order = None` at the start of **every** cancel attempt, with no guard against re-cancelling an already-cancelled booking. If a customer's cancel is ever double-submitted (retry, double-click, a slow network prompting a resend) and that second attempt errors out, the evidence of the **first, genuinely successful** cancellation is silently wiped — a real data-integrity loss, not a cosmetic issue, and the exact thing Phase 9's own list page inherits as a known limitation because of it.

- [ ] Confirm this doesn't change behavior for the first, genuinely new cancel attempt on a still-active booking — only a *second* attempt on an *already*-cancelled one takes the new short-circuit path
- **Test Gate:** `FUNC`/`NEG`/`REGR` — a real second cancel attempt against an already-successfully-cancelled booking returns the same successful result without wiping or re-fetching `cancelled_order`, confirmed by comparing the stored value before and after the second attempt; the existing single-cancel path (`livetracker2.md` §3.5's own original Test Gate) still passes completely unchanged; `livetracker3.md` §9.1's own list-page derivation is re-verified to no longer be able to show a genuinely-cancelled booking as Active, since the underlying data can no longer be silently wiped. **No-duplicate-notification case, added on this section's own self-audit — reasoned about but not yet proven, per this tracker's own established "reasoning alone isn't proof" discipline:** the short-circuit fires inside `trigger_cancel()` itself, before any real dispatch to BPP, so `record_on_cancel_result()` — the only place `notify_booking_cancelled_in_background()` is ever called (`livetracker3.md` §4.1) — never runs a second time; confirmed explicitly by asserting the notification mock/outbox count is unchanged after the second, short-circuited attempt, not merely inferred from where the code lives. A real customer double-submitting a cancel must not receive two "your booking was cancelled" emails.
- [ ] **Test-coverage requirement, matching this section's own new Test Gate case above rather than left implicit:** a dedicated unit test exercising the short-circuit path twice in the same test — first a real successful cancel, then a real second `trigger_cancel()` call on the same transaction — asserting both the identical returned result and the unchanged notification count in one place, not two separate, looser tests that could each pass without actually proving the combined property together.
