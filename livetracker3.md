# BECKN Platform — Functional & UX Completeness Live Tracker

> **Project scope declaration (2026-07-29), inherited from [livetracker1.md](livetracker1.md) (trust layer, closed) and [livetracker2.md](livetracker2.md) (business workflow layer, closed):** this project builds a **private, self-contained Beckn network** — our own Registry, Gateway, BAP, and BPP — that strictly follows the Beckn Protocol Specification and Beckn-ONDC Implementation Guidelines for correctness and interop-readiness. It does **not** connect to, register with, or integrate with the real, live ONDC network. `project_details.md` is never modified — it is the frozen, client-provided brief.

**Scope of this tracker:** Closes the **functional/UX-completeness gaps** found during the full-system production-readiness audit conducted 2026-07-29 (23 findings total, locked and enumerated in the Change Log below) — specifically the subset of those findings that are pure code/feature work, doable and testable entirely at the codebase level, with **no new infrastructure decisions required**. Concretely: search actually filtering by what a customer typed, ratings actually aggregating and surfacing instead of being silently stored and forgotten, real customer-facing UI for rating/support/track (all three exist as fully protocol-compliant, tested backend features today with zero way for an actual person to reach them), notification delivery, a full documentation-freshness sweep, and closing the automated-end-to-end-testing gap. **Payment gateway integration remains explicitly out of scope** — tracked separately as [livetracker5.md](livetracker5.md) (not yet designed). **Infrastructure/scale-readiness work** (Gateway-routing architecture, horizontal scaling, backpressure, secret management, load testing) is a **different kind of work** and is tracked separately as [livetracker4.md](livetracker4.md) — the two were deliberately split into two files rather than folded into one, per the explicit split decision recorded in this tracker's own Change Log.

## How to Use This Tracker

1. Work phases **top to bottom** where a real dependency exists (§2's rating aggregation must exist before §3.1's rating-submission UI can show a meaningful confirmation), but unlike `livetracker1.md`/`livetracker2.md` this tracker is **not** one continuous vertical slice — §1 (search), §2–3 (rating/support/track), §4 (notifications), and §5–6 (docs/testing) are four genuinely independent gap-closure efforts found by the same audit, not sequential building blocks of one feature. Work them in any order that suits real priority; the numbering here reflects the order the audit surfaced them in, not a mandatory build order.
2. A task/subtask is checked `[x]` **only** after its implementation is complete **and** its Testing & Validation Gate passes. Never check a box on implementation alone.
3. A phase is closed **only** after its "Phase Exit — Testing & Sign-off" section is fully checked.
4. If implementation reveals a decision not captured in a component's `*_details.md`, update that file in the same work session with an additive "Implementation note" callout — never rewrite the original client-provided content, and never touch `project_details.md`. Also update whichever root-level doc (`SECURITY.md`, `API_CONVENTIONS.md`, `OBSERVABILITY.md`, `TESTING.md`) the change actually affects.
5. Lifecycle tags on each item show when it's required. §4 (Notifications) is deliberately tagged `[BETA]`, not `[MVP]` — the project owner explicitly confirmed email/SMS delivery is optional, not a blocking gap, during the audit that produced this tracker (see Change Log). Do not build it ahead of its tag; do not skip a tagged item at its own stage.
6. Every finding this tracker closes was reached by **directly reading the running code**, not by re-deriving from documentation — three of the six areas below (§1, §2, §3) were only discovered because a summary-level assumption ("search filters results," "ratings are shown somewhere") turned out to be false on inspection. Any new task discovered while working this tracker should be verified the same way — against the actual code — before being marked a real gap.
7. When a shared module changes after `livetracker2.md`'s business flows already depend on it (e.g. `catalog.py`'s query-filtering logic, touched by §1), re-run the affected downstream test gates from `livetracker2.md` (specifically §3.1/§3.8's search and cache tests) before considering the change safe — the same "prove the whole chain again" discipline used throughout both prior trackers.

**Lifecycle tags:** `[MVP]` build now · `[PILOT]` small real-batch of participants · `[BETA]` broader external participants · `[ENT]` enterprise scale, design-documented now but not built until real scale demands it.

**Test type legend:** `SMOKE` basic runs · `SANITY` narrow correctness check after a change · `FUNC` functional correctness · `POS`/`NEG`/`EDGE` case coverage · `INTEG` cross-service · `E2E` full flow · `REGR` regression · `SEC` security/abuse · `LOAD` concurrency/throughput/performance · `DR` failure-injection/disaster-recovery.

## Phase 1 — Search Correctness (closes Finding #21)

**Objective:** Make `/search` actually filter by what a customer typed. The audit's most severe finding in this tracker: `BAP/backend/core/search_service.py`'s `trigger_search()` correctly places the real query text on the wire (`message.intent.item.descriptor.name`), but `BPP/backend/core/search_service.py`'s `dispatch_on_search()` never reads `payload["message"]["intent"]` at all — it calls `get_cached_catalog(context["domain"])` and returns the entire domain's catalog unfiltered, every time, regardless of what was typed. Confirmed 0/100 on actual query relevance, not a "basic vs. sophisticated" quality question.

### 1.1 Query-Text Filtering in BPP's Catalog Build `[MVP]`
- [ ] `dispatch_on_search()` reads `message.intent.item.descriptor.name` (and, if present, `message.intent.category.descriptor.code`/`message.intent.fulfillment.type`) from the real inbound payload, not just `context["domain"]`
- [ ] `build_catalog()`/`build_beauty_catalog()` (and the Healthcare/Automotive equivalents) gain a real filter step: resources whose `descriptor.name` (and their owning `BusinessAccount`'s descriptor) don't match the query text are excluded from the returned catalog — **word-tokenized, case-insensitive AND-match** (split the query into words, match if every word appears as a substring somewhere in the combined searchable text), not a single literal substring match on the whole query string. A pure literal-substring match would leave a real, common failure mode unfixed: a query like "hair salon" would never match a resource/business descriptor of "Salon Hair Care" (same words, different order) even though that's exactly the kind of real query this fix exists to serve. This is not fuzzy/typo-tolerant matching (still explicitly out of scope, §1.2) — it's the minimum needed for "search actually reflects what was typed" to be true for realistic multi-word queries, matching this project's already-established "no invented sophistication ahead of real need" discipline (§3.8 of `livetracker2.md` set this same bar for caching) without under-shooting the actual, common case.
- [ ] An empty/missing `intent.item.descriptor.name` (a customer browsing without typing anything) falls back to the existing unfiltered full-domain-catalog behavior — not a regression, a defined behavior for the "browse everything" case, which is a real, legitimate use of `/search`
- [ ] `get_cached_catalog()`'s existing cache key (§3.8 of `livetracker2.md`, currently keyed on domain only) is re-examined: caching per-query-text would explode cache cardinality for a low, real hit-rate benefit, so the correct fix is caching the **unfiltered** per-domain catalog as today (unchanged) and applying the new query filter **after** the cache read, on the (already fast, in-memory) result — not a cache-design change, a filter-placement decision, recorded here explicitly rather than left for whoever implements it to guess
- **Test Gate:** `FUNC`/`NEG`/`REGR` — a real search for "Priya" (an existing seeded stylist's descriptor name) returns only resources matching that text, not the full catalog; a search for a nonsense string returns zero results, not an error; an empty query still returns the full domain catalog (unchanged prior behavior); `livetracker2.md` §3.1's existing search E2E test and §3.8's cache-hit/invalidation tests are re-run and still pass, proving this change didn't regress the already-proven cached-search path.

### 1.2 Basic Relevance Ranking (stretch, not required for this gap to close) `[BETA]`
- [ ] Once exact/substring filtering (§1.1) is real, order multiple matching results by a simple, honest signal already available in the data model — e.g. `Rating.average_rating` (built in Phase 2 of this tracker) descending, ties broken by resource creation order — rather than leaving result order as an accidental database-iteration artifact
- [ ] Explicitly **not built** here: fuzzy/typo-tolerant matching, a real search-relevance engine (Elasticsearch/Postgres full-text search with `tsvector` ranking), personalization — these would be genuine over-engineering for this project's current scale and were never named as a requirement by the audit finding (#21) or `project_details.md`; substring matching plus a simple honest ranking signal closes the real gap (search ignoring the query entirely) without inventing scope the finding never asked for
- **Test Gate:** `SANITY` — with two matching resources of different average ratings, the higher-rated one is returned first; this bullet is optional and may be deferred without blocking Phase 1 Exit if the project owner deprioritizes it once §1.1 closes the actual severity-0 gap.

### Phase 1 Exit — Testing & Sign-off
- [ ] §1.1's Test Gate passes
- [ ] §1.2 explicitly decided (built or consciously deferred) — not silently skipped without a recorded reason
- [ ] `livetracker2.md`'s own §3.1 (Discovery) and §3.8 (Performance/Cost) sections gain a one-line pointer to this fix, since this tracker corrects behavior those sections originally signed off on without this gap having been caught yet — matching the "corrections are new entries, never silently rewritten history" discipline both prior trackers already established
- [ ] Sign-off recorded

## Phase 2 — Rating Lifecycle Completion (closes Finding #22)

**Objective:** Close the "stored but never surfaced" gap for ratings. `Rating` (built in `livetracker2.md` Phase 4.5) correctly receives, validates, and stores real `/rating` submissions — a direct grep for `average_rating|avg_rating|Avg(|rating_count|aggregate.*[Rr]ating` across `BPP/backend/core` and `shared/inventory_core` returned zero matches. A rating is saved and then never appears anywhere again: not in search results, not on a provider's profile, nowhere. The customer-facing value of having submitted one is currently zero.

### 2.1 Rating Aggregation `[MVP]`
- [ ] A real aggregation mechanism computing, per rated entity (keyed the same way `Rating.entity_id`/`rating_category` already resolves against a `Booking` per `livetracker2.md` §4.5's own design), an `average_rating` and `rating_count` — decide explicitly whether this is computed on write (incremental update at `/rating` submission time, matching this project's established "synchronous core, no invented async step" discipline for anything that isn't genuinely a scale problem yet) or via a periodic sweep (mirroring the existing `sweep_expired_holds()`/`sweep_completed_bookings()` pattern in `shared/inventory_core/reconciliation.py`) — the on-write approach is the honest default absent a real scale reason for the sweep approach, since rating submission volume is nowhere near what would make an inline aggregate update a real bottleneck
- [ ] Aggregation is scoped correctly per `Rating.rating_category`: an `Order`/`Fulfillment`-category rating (the two categories this project's flow actually produces today, per §4.5's own resolution logic) rolls up to the `Resource`/`Provider` the underlying `Booking` belongs to — not conflated with `Item`/`Agent`/`Support`-category ratings, which this project's own rating submissions have never actually populated but which the schema still allows and the aggregation must not silently mis-bucket if one ever arrives
- [ ] **Security correction, found during this tracker's own final audit pass (2026-07-29) — the original draft of this bullet was wrong and would have shipped a reputation-manipulation hole.** A rating submitted against a booking the calling transaction doesn't own (the existing, already-correct IDOR handling from §4.5 — captured as real feedback, just not FK-linked) is **excluded from the public-facing `average_rating`/`rating_count`**, not counted in it as originally drafted. Reasoning: `rating_category`/`entity_id` on an unlinked submission are caller-supplied and unverified against any real booking — counting them toward the public number would let anyone submit unlimited ratings against any resource they name, with no requirement to have ever booked it, directly enabling review-bombing (tanking a competitor) or self-inflation (rating your own resource from a throwaway transaction). Only ratings that successfully FK-link to a real `Booking` the calling transaction genuinely owns are aggregate-eligible; unlinked submissions are still stored (existing §4.5 behavior, unchanged) for audit/investigation purposes only, never rolled into the number a customer sees.
- [ ] **Duplicate-submission handling, not addressed in the original draft.** One rating per `(Booking, rating_category)` from its true owning transaction: a second `/rating` call against the same already-rated booking updates the existing `Rating` row in place (the honest, real-world-correct behavior — "I meant to give 5 stars, not 3" is a legitimate correction, not abuse) rather than being silently rejected or double-counted in the aggregate. A DB-level uniqueness constraint on `(booking, rating_category)` enforces this is never violated even under a race (two near-simultaneous submissions for the same booking).
- [ ] **Rate-limiting coverage gap, found during this tracker's own final audit pass — must be verified, not assumed either way.** `livetracker2.md` §3.7 built Redis-backed rate limiting for the original 8 wire actions; `/rating`/`/support` were built later, in Phase 4.5, after §3.7's own endpoint list was written. Confirm directly (grep `rating_service.py`/`support_service.py` for the existing rate-limit decorator) whether that coverage was ever actually extended to these two endpoints. If not — a real, live gap, not a hypothetical — extend the same mechanism to both before this phase closes; without it, the abuse vector the bullet above just closed by construction (aggregate-eligibility) is still reachable as a pure volume/DoS problem against the unlinked-but-stored feedback table, and `/support` remains unprotected against simple spam.
- [ ] **Input-validation gap, found on this tracker's own second audit pass — the aggregation design as drafted assumed a data shape the real schema doesn't guarantee.** `protocol_compliance_notes_v1.1.md` §O already confirms `Rating.value` is deliberately a free-form string, since the real `Rating.yaml` schema allows it to carry a bare number *or* a comparison/logical expression (`gt`/`gte`/`&&`). This project's own UI (§3.1) only ever submits a clean `"1"`–`"5"` string, but `/rating` is still a real wire action any BAP-side caller can hit directly, not gated to this project's own frontend — a non-numeric or out-of-range `value` must be explicitly rejected (or excluded from aggregation with the submission still stored, matching the IDOR-mismatch handling above) at write time, not silently crash the aggregate computation or silently corrupt it with a `NaN`/type-coercion artifact. Decide and implement explicitly: this project's own use case only ever needs a plain integer 1–5, so `/rating` validates `value` against that range before accepting it as aggregate-eligible, honestly narrower than the full schema's own latitude (the same "modeled honestly, used minimally" precedent §O itself already set for this exact field).
- **Test Gate:** `FUNC`/`EDGE`/`SEC` — three real ratings (4, 5, 3) submitted by the true owning transaction against the same resource produce `average_rating == 4.0`, `rating_count == 3`; a rating against an entity with zero prior ratings correctly initializes rather than dividing by zero or erroring; a rating submitted against a booking the caller doesn't own is stored but **provably does not move** that resource's public `average_rating`/`rating_count`, confirmed by comparing the aggregate before and after; a second real rating from the true owner against the same booking updates the existing entry rather than creating a second one or double-counting; a rapid-fire burst of `/rating`/`/support` calls is throttled the same way the original 8 actions already are; a `/rating` submission with a non-numeric or out-of-range `value` (e.g. `"gte 3"`, `"99"`, `""`) is cleanly rejected with a standard error, never reaching the aggregation function or crashing it; re-running the full Phase 4.5 rating test suite from `livetracker2.md` still passes unchanged, proving this is additive, not a regression of the existing storage/IDOR behavior.

### 2.2 Surface the Aggregate to Real Users `[MVP]`
- [ ] `build_catalog()`/`build_beauty_catalog()` (and Healthcare/Automotive equivalents) populate `Provider.rating`/`Item.rating` — the real `Rating.yaml#/properties/value` scalar `$ref` already confirmed against the official schema in `protocol_compliance_notes_v1.1.md`'s Provider/Item grounding — with the real aggregate from §2.1, not left unset as it is today
- [ ] BPP's staff/owner-facing dashboard (the real screen built in `livetracker2.md` §4.4) gains a visible average-rating display on each `Resource` — the business side seeing its own real rating is the most direct, lowest-effort way to make this feedback loop matter to the people who can act on it
- [ ] The customer-facing search-results screen (`livetracker2.md` §3.9's real screen) displays each result's average rating and count, once §1's search-filtering fix and this section are both live — reusing the already-established Base component library (loading/empty/error states) rather than inventing new UI patterns
- **Test Gate:** `E2E` — a real rating submitted against a real resource is reflected in that resource's next `/search` result and on BPP's dashboard, within the same request cycle (no stale-until-next-deploy behavior) — verified live against the real Docker stack, following the same "not just claimed, proven" discipline both prior trackers held throughout.

### Phase 2 Exit — Testing & Sign-off
- [ ] §2.1 and §2.2 Test Gates pass
- [ ] `livetracker2.md` §4.5's own entry gains a one-line pointer noting aggregation/display was completed here, in this tracker, rather than silently leaving that phase's own Change Log looking like the whole rating feature was finished then
- [ ] Sign-off recorded

## Phase 3 — Customer-Facing UI Completion for Rating, Support, Track (closes Finding #23)

### 3.3 Track UI `[MVP]`
