# BECKN Platform — Infrastructure & Scale-Readiness Live Tracker

> **Project scope declaration (2026-07-29), inherited from [livetracker1.md](livetracker1.md) (trust layer, closed) and [livetracker2.md](livetracker2.md) (business workflow layer, closed):** this project builds a **private, self-contained Beckn network** — our own Registry, Gateway, BAP, and BPP — that strictly follows the Beckn Protocol Specification and Beckn-ONDC Implementation Guidelines for correctness and interop-readiness. It does **not** connect to, register with, or integrate with the real, live ONDC network. `project_details.md` is never modified — it is the frozen, client-provided brief.

**Scope of this tracker:** Closes the **infrastructure/scale-readiness gaps** found during the full-system production-readiness audit conducted 2026-07-29 (23 findings total, locked and enumerated in [livetracker3.md](livetracker3.md)'s Change Log) — specifically the subset of those findings that require real architectural/infrastructure decisions, as distinct from `livetracker3.md`'s pure code/feature gaps. **Pushed as far as possible entirely at the codebase level**: the Gateway-routing architecture correction, real event-driven/async maturity, secret-management integration, horizontal-scale correctness, backpressure, load-testing tooling, multi-tenancy defense-in-depth, and deployment automation are all real, testable-locally engineering work. **Real cloud deployment itself is explicitly excluded from this tracker** — it needs actual provisioned infrastructure to exist first, which is its own separate, later, not-yet-scoped area, exactly parallel to how payment gateway integration is its own separate area ([livetracker5.md](livetracker5.md), not yet designed). This tracker makes the codebase genuinely ready to deploy onto real infrastructure when that later decision is made — it does not make that later decision for it. **Added 2026-07-30, found live outside the original 23-finding audit, same as three equivalent findings this session added to `livetracker3.md`:** §3.3, Subscribe batching — the real Subscribe payload's `network_participant` array supports registering a participant across multiple domains in one call, but this project has only ever sent one domain per call, found while re-onboarding participants for Healthcare/Automotive during this tracker's own §1.3 live verification.

## How to Use This Tracker

1. Work phases **top to bottom where a real dependency exists** — §1 (Gateway-routing fix) changes how every post-search action is called, so it should land before §5's multi-participant proof re-exercises those same call paths at scale. Otherwise, like `livetracker3.md`, this is not one continuous vertical slice — the 8 phases below are independent gap-closures the same audit surfaced, not sequential steps of one feature.
2. A task/subtask is checked `[x]` **only** after its implementation is complete **and** its Testing & Validation Gate passes. Never check a box on implementation alone.
3. A phase is closed **only** after its "Phase Exit — Testing & Sign-off" section is fully checked.
4. **Codebase-level discipline, explicit and load-bearing for this entire tracker:** every phase here must be buildable and testable against the existing local `docker compose` stack, with no dependency on a real cloud account, a real external secrets service, or real external traffic existing yet. Where a task's *complete* real-world form genuinely requires infrastructure that doesn't exist yet (e.g. a production KMS, a real multi-region deployment), the task is scoped down to the honest, complete-at-this-scale local equivalent (e.g. a local secrets-abstraction layer that a real KMS could later be swapped behind) — matching the exact discipline `livetracker2.md` §4.6 already used for its Scale-Readiness *design* work, now applied to real, running code instead of prose.
5. If implementation reveals a decision not captured in a component's `*_details.md`, update that file in the same work session with an additive "Implementation note" callout — never rewrite the original client-provided content, and never touch `project_details.md`. Also update whichever root-level doc the change actually affects, per the list above.
6. Lifecycle tags show when each item is required; `[ENT]` items here are genuinely scale-triggered (build only once a real, measured need exists), not an excuse to defer core correctness work that's actually due now (e.g. §1's protocol-routing fix is `[MVP]` — it's a correctness gap, not a scale one).
7. When a shared module changes here after `livetracker2.md`'s business flows already depend on it (e.g. §1 removing Gateway's relay logic, §2 changing how events are consumed), re-run every downstream test gate from `livetracker2.md` that exercises the same path — the full 10-action E2E suite for §1, the audit-log/metrics consumer tests for §2 — before considering the change safe. This is the same "prove the whole chain again, not just the new part" discipline used throughout both prior trackers.

**Lifecycle tags:** `[MVP]` build now · `[PILOT]` small real-batch of participants · `[BETA]` broader external participants · `[ENT]` enterprise scale, design-documented now but not built until real scale demands it.

**Test type legend:** `SMOKE` basic runs · `SANITY` narrow correctness check after a change · `FUNC` functional correctness · `POS`/`NEG`/`EDGE` case coverage · `INTEG` cross-service · `E2E` full flow · `REGR` regression · `SEC` security/abuse · `LOAD` concurrency/throughput/performance · `DR` failure-injection/disaster-recovery.

## Phase 1 — Protocol-Correct Routing: Gateway Scope Fix (closes Finding #4)

**Objective:** Bring this project's actual routing behavior in line with the core Beckn protocol's own confirmed design (`protocol_compliance_notes_v1.1.md` §P): only `/search` goes through the Gateway; every other action (`select`/`init`/`confirm`/`status`/`cancel`/`update`/`track`/`rating`/`support`) goes directly BAP↔BPP. This is the single largest architectural change in this tracker — it touches Gateway, BAP, and BPP together, plus their tests and docs, not just one app.

### 1.1 BAP-Side Direct Dispatch `[MVP]` — implementation & test-suite verification **CLOSED 2026-07-30**
- [x] BAP's `SearchSession` (or its `on_search` result-handling path) captures the winning BPP's real `bpp_uri`/`bpp_id` from the `context` object of the `/on_search` response that produced the transaction's chosen result — the exact field the protocol itself uses to make Gateway's role unnecessary after discovery, per §P.3
- [x] Each of `select_service.py`/`init_service.py`/`confirm_service.py`/`status_service.py`/`cancel_service.py`/`update_service.py`/`track_service.py`/`rating_service.py`/`support_service.py` (BAP) is changed to call the resolved `bpp_uri` directly, signed with BAP's own key (the existing sign mechanism, unchanged), instead of calling Gateway's `dispatch_X` endpoint
- [x] BAP's dedicated `get_gateway_client()` (built in `livetracker2.md` §3.6 specifically to isolate Gateway-bound calls' circuit breaker from Registry-bound calls) is retired for these 9 actions and replaced by a new `get_bpp_client(bpp_uri)` — mirroring Gateway's own existing `get_participant_client(subscriber_id)` per-counterparty breaker-isolation pattern (`livetracker2.md` §3.6) rather than inventing a new resilience primitive; `/search` alone keeps using `get_gateway_client()`, since that's the one action that still legitimately goes through Gateway
- [x] **Real gap found and closed by design audit before implementing, not after (2026-07-29): a protection this project already built and closed once would silently regress by omission.** `livetracker2.md` §3.2/§3.3 explicitly closed a gap where a BPP's `SUBSCRIBED` status can go stale between search and a later action — Gateway's `dispatch_select`/`dispatch_init` re-check Registry fresh before forwarding, specifically to catch this. Once BAP calls the resolved `bpp_uri` directly, nothing performs that re-check unless it's explicitly assigned somewhere — this task assigns it to BAP: each of the 9 direct-dispatch call sites performs its own fresh `registry_client.lookup()` `SUBSCRIBED`-status check on the target BPP immediately before dispatching, using the same Registry-lookup mechanism BAP already has for verifying inbound signatures, not a new one. Skipping this would mean a deactivated/deregistered BPP could still receive and process a direct `confirm`/`cancel`, a real trust-chain regression this tracker must not reintroduce while fixing something else.
- [x] **Refinement, found on this tracker's own second audit pass: the fresh lookup must also supply the address actually dialed, not just gate a separately-cached one.** A naive reading of the bullet above would re-check `SUBSCRIBED` status via a fresh lookup but still dispatch to the `bpp_uri` originally captured from the old `/on_search` context — if a BPP has genuinely re-onboarded with a new `subscriber_url` since that search (a real, already-observed scenario in this project's own history, per `livetracker2.md`'s repeated re-onboarding-cycle entries), the status check would correctly pass while the request is still sent to a stale or dead address. The fresh Registry lookup's own returned `subscriber_url` **is** the dispatch target for that call, not merely a pass/fail gate sitting in front of a separately-remembered one — status-check and address-resolution are the same lookup, not two.
- [x] **Second gap found the same way: correlation-ID propagation moves, not disappears.** `livetracker2.md` §3.10 wired `X-Correlation-Id` propagation for `confirm`/`cancel`/`update` specifically through Gateway's `dispatch_confirm`/`dispatch_cancel`/`dispatch_update` forwarding the header on its relay call. With Gateway retired from these 3 actions' path, BAP's own `trigger_confirm`/`trigger_cancel`/`trigger_update` must set `X-Correlation-Id` directly on the now-direct call to BPP, and BPP's corresponding views must read it directly from the inbound request instead of from Gateway's relay — the same one id spanning BAP→BPP for a single action, just one hop shorter than before, not a dropped feature.
- **Test Gate:** `FUNC`/`INTEG`/`SEC` — a real `select` call from BAP is observed (via `docker logs`/network capture) going directly to BPP's own container address, never touching Gateway's container at all, for all 9 post-search actions; a direct `select`/`init` call against a BPP that was deactivated (`is_active=False`/deregistered from Registry) *after* the customer's original search is correctly rejected by BAP's own fresh re-check, not silently forwarded; a BPP that re-onboards with a genuinely new `subscriber_url` between search and a later action is dispatched to correctly at the *new* address, not the stale one captured at search time, proving the fresh lookup's own URL is what's actually dialed; a real `confirm` call's `X-Correlation-Id` is observed identical on BAP's outbound request and BPP's audit-log entry for that action, with no Gateway hop in between. **PASSED 2026-07-30, real Docker stack + real test suites, not mocked/simulated — with one honestly-recorded exception.** Independently verified (not just agent-claimed): both `get_bpp_client()`/`resolve_subscribed_bpp()` (`BAP/backend/core/registry_client.py`) built and confirmed live; all 9 BAP service files updated and each app's full backend test suite re-run by me directly in freshly rebuilt Docker containers — **215/215 BAP passed**, matching the implementing agent's own reported count exactly. Live spot-check: a real `select` call was driven through the live stack while tailing `docker compose logs beckn-gateway` — zero log lines appeared for it, while `bpp-backend`'s own log showed `POST /select` handled directly, confirming zero Gateway involvement. Deactivated-BPP rejection and re-onboarded-BPP new-address dispatch were both live-proven with real Registry state mutations during §1.3 below (see that section's own evidence) — restored cleanly afterward. **The one exception, found and recorded honestly, not glossed over:** the `X-Correlation-Id` log-based proof this Test Gate names could not be produced as literally described — there is no log line at all on a successful confirm on either side, and a pre-existing, unrelated `CorrelationIdMiddleware` context-unwind timing bug loses the id before Django's own automatic error-path logging captures it. Confirmed by direct code read instead that the same `correlation_id_var.get()` value is synchronously forwarded (no thread boundary) as the `X-Correlation-Id` header on every direct call — the mechanism is real and correct, just not provable via the specific log-grep method this Test Gate names. Flagged as a genuine, still-open follow-up (see §1.3's own Change Log entry), not silently marked closed.

## Phase 2 — Event-Driven & Async Architecture Maturity (closes Findings #5, #7, #10)

**Objective:** Close the gap the audit found identically from three separate angles (event-driven implementation, async/callback implementation, error-handling's DLQ caveat): `shared/event_bus`'s own code comment already states plainly that no independent, multi-worker consumer pool exists anywhere in this codebase — everything that "reacts" to a booking event (audit log, metrics, WebSocket push, and `livetracker3.md` §4's new notification consumer) runs directly and synchronously, inline, in the same request path that created the event. That's a well-structured audit/notification log today, not yet a genuine decoupled event-driven system.

### 2.1 Independent Async Consumer / Worker Pool `[MVP]`
- [ ] A real, separate consumer process (not a request-path inline call) reading from `shared/event_bus`'s existing Redis-backed queue — the smallest correct implementation for this project's current single-process-per-app deployment model is a dedicated management command / long-running worker process per app (BAP, BPP), started as its own container/process, not a new heavyweight broker dependency (Celery+beat, Kafka) that would be real over-engineering relative to this project's actual current event volume
- [ ] Existing inline consumers (audit-log writes, business-metrics increments, WebSocket broadcasts, `livetracker3.md` §4's notification sends) are migrated to run inside this new worker process, reading events off the real queue, instead of being called directly from `reservation.py`'s booking-lifecycle functions — the producer side (`publish_event()`) is unchanged; only how consumers receive events changes
- [ ] The already-proven per-entity event-ordering guarantee (`livetracker2.md` §1.4) and idempotency wrapper (`process_with_dlq`) are preserved exactly, reused by the new worker rather than reimplemented — this phase changes *where* consumption happens, not the correctness guarantees already built and tested around it
- [ ] **No-regression cutover requirement, found on this tracker's own "no dip in the graph" audit pass (2026-07-29), the same class of risk §1.3/§1.4 was just reordered to avoid.** Business metrics (`livetracker2.md` §3.10) are the only thing measuring `project_details.md`'s own named 95% booking-success-rate KPI, and audit logs are the only durable record of booking lifecycle events — an atomic "delete the inline call, hope the new worker picks it up" cutover risks a real, live blackout of both if the new worker fails to start, points at the wrong queue, or has any startup bug, and nobody would necessarily notice immediately since the booking action itself still succeeds (the consumer failure is silent from the customer's side). Fixed sequencing: run the new worker **alongside** the still-present inline calls first (both consume the same event; the existing idempotency ledger makes this double-processing safe, not corrupting), confirm live for a real burn-in period that the worker's own output matches the inline path's exactly (same metrics counts, same audit-log entries), and only then remove the inline calls — mirroring §1.3/§1.4's now-explicit "prove before you remove the fallback" discipline instead of reintroducing the same risk in a different subsystem.
- **Test Gate:** `FUNC`/`INTEG`/`DR` — a real booking confirmation produces a `BookingConfirmed` event that is consumed by the new, separate worker process (confirmed by process/PID inspection, not just by the side effect happening) — not inline in the same request/thread that created it; killing the worker process mid-consumption and restarting it resumes correctly, without double-processing or dropping the event (reusing the existing idempotency ledger); during the parallel-run window, a deliberately broken/stopped new worker produces **zero visible change** to metrics/audit-log output (the inline path is still covering it), proving the cutover itself introduces no blackout window before the inline calls are actually removed.

### 2.2 Event Replay & Recovery `[MVP]`
- [ ] A durable, queryable event log (distinct from the transient work-queue itself) — the existing `BookingAuditLogEntry`/`ProcessedEvent` models already persist enough to reconstruct a booking's real event history; this task is about proving that history can genuinely be **replayed** to rebuild a consumer's state after a failure, not just read for a human audit trail
- [ ] A real replay tool/management command: given a time range or a specific entity, re-drive its recorded events through a (freshly-registered, or previously-behind) consumer — explicitly distinct from the existing reconciliation sweeps (`sweep_expired_holds`/`sweep_completed_bookings`/catalog-cache reconciliation), which are periodic *state-comparison* corrections, not event replay
- **Test Gate:** `FUNC`/`DR` — deliberately disable the metrics consumer, drive 3 real bookings through confirm, re-enable the consumer, run the replay tool for that time window, and confirm the business-metrics counters correctly reflect all 3 bookings after replay — not just the ones that happened to be consumed live.

### 2.3 Dead-Letter Queue Live-Proof `[MVP]`
- [ ] The existing `EVENT_BUS_DLQ_NAME` config and `process_with_dlq` mechanism (referenced throughout `livetracker1.md`/`livetracker2.md` but, per the audit, never actually proven live) is deliberately exercised: a consumer is made to fail deterministically for one specific event, and the event's real arrival in the DLQ (not just the config existing) is confirmed by direct inspection
- **Test Gate:** `DR` — a poisoned event lands in the real DLQ after exhausting retries, confirmed via direct Redis inspection, matching `livetracker2.md` §1.4's own Test Gate wording ("a deliberately poisoned event lands in the DLQ instead of retrying forever") — this phase is what actually proves that claim live for the first time, rather than trusting the unit-test-only coverage it previously had.

### 2.4 BAP-Side Reconciliation Sweep Parity (closes part of Finding #9) `[MVP]`
- [ ] BPP has automatic reconciliation sweeps for its own state (expired holds, catalog-cache drift, completed bookings — all built in `livetracker2.md` §3.11/§4.5); BAP has no equivalent — if a callback is ever lost, a customer currently has to manually re-trigger `/status` to resync, with no background job catching that automatically on BAP's side
- [ ] A new BAP-side periodic sweep, mirroring BPP's existing `sweep_expired_holds()`/reconciliation pattern (`shared/inventory_core/reconciliation.py`): for any `SearchSession` whose last-known stage result is stale beyond a defined threshold, re-issue a `/status` check against the resolved BPP directly (using §1's new direct-dispatch path) and update the session's real state
- **Test Gate:** `FUNC`/`DR` — deliberately drop a real `on_confirm` callback (simulating a lost message) and confirm BAP's new sweep detects the stale session and self-heals it to the correct real state within one sweep interval, without manual customer action.

## Phase 3 — Trust & Secret Management Hardening (closes part of Finding #3)

**Objective:** Close the trust/cryptography-layer gaps this tracker has found — originally two from the audit (Section 15.6 production secret-handling and the replay-protection section of the Beckn-ONDC implementation guidelines, both previously accepted as known `[MVP]`-stage limitations, now in scope to actually close), plus a third found live outside that original audit (§3.3, Subscribe batching — see this tracker's own Change Log for how).

### 3.1 Nonce/Message-ID Replay Protection `[MVP]`
- [ ] **Reconciliation against a prior tracker's own closed decision, found on this tracker's own cross-tracker sync audit (2026-07-29) — must be resolved explicitly, not silently overridden.** `livetracker1.md` Phase 4 (signed off 2026-07-15) examined this exact behavior and deliberately did **not** fix it, recording: *"a validly-signed request can be replayed as-is within its ~30s `created`→`expires` window... correctly identified as a characteristic of the confirmed protocol's nonce-less Authorization scheme, not a bug to silently patch with an invented mechanism."* That reasoning was correct at the time, for what that phase was building: a bare, protocol-literal trust layer with no customer-facing traffic yet. It is being consciously revisited here, not contradicted by accident: (1) the Beckn-ONDC implementation guidelines' own Section on replay protection recommends message-ID tracking as a real hardening measure *beyond* the bare protocol minimum, the same category of "beyond-baseline" hardening this project already chose for other things the protocol doesn't mandate (e.g. the Idempotency-Key mechanism, `livetracker2.md` §3.6); (2) this tracker's own audit (`livetracker3.md`'s Change Log) re-scored this specifically because the system now carries real customer-facing booking traffic across 3 domains, a materially different exposure than the trust-layer-only system `livetracker1.md` Phase 4 was built against. This is a deliberate upgrade of the security bar as the system matures, not a reversal of a mistake — but it must be recorded as such in both directions: this bullet here, and a corresponding addendum in `livetracker1.md`'s own Change Log (added the same way that tracker's own 2026-07-19 header-name correction was added after its formal close — a precedent for revisiting a closed tracker's record without rewriting it) so a future reader of `livetracker1.md` doesn't take its "not a bug" framing as still the final word.
- [ ] Today's freshness check is timestamp-only — a signed request can be replayed as-is within its validity window, a real gap the implementation guidelines call out explicitly (real protection needs *both* timestamp freshness *and* unique message-ID tracking)
- [ ] A real, Redis-backed "seen message ID" set (short-TTL, matching the signed request's own validity window — no need to remember an ID longer than the window during which replaying it could matter) checked at the same signature-verification chokepoint every action already uses, rejecting an already-processed message ID even if its timestamp is still technically valid
- [ ] Applies uniformly across all three apps that verify incoming signed requests (Registry, BAP, BPP) and Gateway's own `/search`-only verification post-§1 — the same one-mechanism-everywhere discipline already used for rate limiting and circuit breakers throughout both prior trackers
- [ ] **The single most important correctness risk in this phase, found by design audit before implementing, not discovered as a production incident later: naive nonce rejection will break this project's own already-proven resilience mechanism.** `shared/resilient_http` (built and live-tested in `livetracker1.md`/`livetracker2.md`, `HTTP_CLIENT_MAX_RETRIES=3`) retries a request on timeout/network failure — if that retry resends the identical, already-signed payload bytes (same message ID, same signature), a receiver correctly enforcing message-ID uniqueness would reject the legitimate retry as if it were an attacker's replay, silently breaking a resilience path this project has relied on and live-tested since Phase 4.2 of `livetracker1.md`. The fix: `resilient_http`'s retry path must generate a fresh timestamp and message ID and **re-sign** on every attempt — a retry is a new, independently-valid signed request carrying the same business payload, not a resend of the same wire bytes. This is a real code change to `shared/resilient_http`, not just a note; it must land in the same PR as the nonce-rejection mechanism itself, not after, since deploying one without the other would either break real retries (nonce lands first) or leave replay protection unverified (retry-fix lands first without anything to test it against).
- **Test Gate:** `SEC`/`INTEG` — a captured real signed request, replayed byte-for-byte within its original validity window, is now correctly rejected as a duplicate; a genuinely new request with a fresh message ID is unaffected; a deliberately forced network timeout on a real `confirm` call causes `resilient_http` to retry with a fresh nonce/signature, and that retry is correctly accepted by BPP, not rejected as a replay — this specific case is the one this phase must not regress, and is tested explicitly, not assumed safe because the two mechanisms were each tested in isolation.

### 3.2 Secret Management Abstraction `[MVP]`
- [ ] Today, signing/encryption private keys sit as plain files in a Docker volume — real, but with no abstraction layer standing between "where a key is stored" and "how application code reads it," which is what actually makes swapping in a real secrets manager (Vault, AWS/GCP KMS) later a config change instead of a code change
- [ ] A thin `shared/` secret-provider interface (mirroring `shared/inventory_core/domain_adapter.py`'s own established registry-interface pattern: an abstract provider + a `get_secret_provider()` resolver) with one real, honest implementation for now — the existing file-based reader, wrapped behind the new interface rather than called directly — so every place that currently reads a key file directly goes through one chokepoint
- [ ] Explicitly **not built now**: an actual Vault/KMS integration itself — that requires a real external service this tracker's own codebase-level scope doesn't have access to; the interface is what makes that a future, low-risk swap instead of a rewrite, matching this tracker's own stated discipline of scoping infrastructure-shaped work down to its honest, complete-at-this-scale local equivalent
- **Test Gate:** `FUNC`/`SANITY` — every existing key-read call site (Registry/BAP/BPP onboarding, signing, verification) goes through the new interface with zero behavior change, confirmed by re-running the full existing trust-layer test suite from `livetracker1.md` unchanged; a second, fake "always-fails" provider implementation, swapped in via config only, correctly causes a clean, well-handled startup error rather than a silent key-read failure deep in a request path — proving the abstraction boundary is real, not cosmetic.

### 3.3 Subscribe Batching Per the Real Protocol Shape (new finding, found 2026-07-30) `[BETA]`
- [ ] **Objective, grounded directly in official protocol text, not inferred:** `protocol_compliance_notes_v1.1.md` §A.2/§B.3 already documents that the real Subscribe payload's `network_participant` field is an **array**, and its own note says plainly: *"one call can register a participant across multiple domains/roles."* Confirmed by direct read of `onboarding_service.py` (identical in BAP/BPP/Gateway) that `submit_subscribe()` always sends exactly **one** `network_participant` entry per call — this project has only ever onboarded one domain per Subscribe call, requiring N separate calls for N domains, found live while re-onboarding BAP and Gateway for Healthcare/Automotive during this tracker's own §1.3 verification.
- [ ] **Honest scoping, not urgency-inflated:** each individual call today is still fully protocol-valid — a single-entry array is a legal array — and the functional outcome is identical either way (Registry ends up with the same per-domain `SUBSCRIBED` state regardless of whether it arrived via 1 batched call or N separate ones). At this project's current scale (3 domains, well under the real 10-calls/minute Subscribe rate limit), this is a genuine spec-compliance/efficiency gap, not a correctness defect — tagged `[BETA]` rather than `[MVP]`, matching this project's own repeated "no invented sophistication ahead of real need" discipline (the same judgment already applied to search ranking, RLS, and the event broker elsewhere in this tracker); revisit at real scale (many domains, or many participants onboarding at once) where N round-trips actually costs something measurable.
- [ ] `submit_subscribe()` (all three apps) extended to accept a list of domains and build one `network_participant` array entry per domain in a single call, rather than being called once per domain by its own caller (`onboarding_subscribe` management command's own domain-iteration loop, if any, folds into this single call too)
- [ ] **Real, more serious gap found by direct read of Registry's own receiving code before this item was implemented, not discovered after the fact: the server side would silently drop every domain but the first.** `registry/core/registry_service.py`'s `handle_subscribe()` (line 144) and `verify_subscribe_authorization()` (line 91) both hardcode `payload["message"]["network_participant"][0]` — building the client-side batching above without fixing this would mean a call listing 3 domains creates exactly **1** `Participant` row (whichever domain happens to be at index 0) and silently never registers the other 2 — a real regression relative to today's working, if inefficient, 3-separate-calls approach, not an improvement. Fixed here, not left implicit: `handle_subscribe()` must loop over every entry in `network_participant` and `update_or_create()` one `Participant` row per domain; `_verify_domain_ownership()` (called once inside the current single-entry path) is confirmed genuinely domain-agnostic by its own parameter list (`subscriber_url`/`signing_public_key`/`request_id`/`subscriber_id`, none of them domain-specific) and so correctly runs **once per call**, not once per domain, when this is fixed. `verify_subscribe_authorization()`'s own `network_participant[0]`-based lookup (used only to find the *existing* row's signing key for a re-subscribe/rotation check) is deliberately left as-is — reusing the exact same "a real participant uses the same signing key across its domains" simplification this codebase already makes explicitly for Lookup authorization (`verify_lookup_authorization`'s own docstring, line 113-115), not a new, unreviewed assumption.
- [ ] **Second, deeper gap found the same way, one level past row-creation: challenge dispatch is per-row, not per-call.** Direct read past the `update_or_create()` call confirmed `handle_subscribe()` calls `_log_audit(participant=participant, ...)` and `_dispatch_on_subscribe_challenge(participant, ...)` against the **specific `Participant` row** just created/updated — each row's `status` only ever transitions from `UNDER_SUBSCRIPTION` to `SUBSCRIBED` via its own independent challenge-response cycle (confirmed by `handle_on_subscribe`'s own bulk-update pattern referenced elsewhere in this project's own onboarding-bug history, `RUNBOOK.md`'s Phase 4.2 entry). Looping the row-creation without also looping the audit-log call and the challenge dispatch would mean only the last-created row ever gets a real challenge — the other domains would get a real `Participant` row but sit at `UNDER_SUBSCRIPTION` forever, never actually completing Subscribe, a real regression *worse* than today's approach (today, every separate call reliably reaches `SUBSCRIBED`). Fixed here: both `_log_audit()` and `_dispatch_on_subscribe_challenge()` move inside the per-domain loop, called once per created/updated row, exactly matching today's single-entry behavior repeated N times within one call — not collapsed into a single call for the whole batch.
- **Test Gate:** `FUNC`/`INTEG`/`NEG` — a single real Subscribe call listing all of this participant's intended domains at once is accepted by Registry and results in one correctly-`SUBSCRIBED` `Participant` row **for every domain listed, not just the first, and not just the last** — confirmed each row independently completes its own real on_subscribe challenge-response and reaches `SUBSCRIBED`, not just gets created at `UNDER_SUBSCRIPTION` and left there; domain-ownership verification is confirmed to run exactly once per call (not once per domain) via a call-count assertion; re-running the existing onboarding test suites (all three apps, plus Registry's own) confirms zero regression to the single-domain case, which must keep working unchanged for any caller that still only wants one domain per call.

## Phase 7 — Multi-Tenancy Defense-in-Depth (closes Finding #18) `[BETA]`

**Objective:** Multi-tenancy isolation is well-tested at the application layer today (real cross-business IDOR tests pass, domain-scoped cache invalidation, `owner_ref`-based scoping throughout) — but it's entirely application-enforced. There's no database-level backstop that would still protect tenant data if a future query ever forgot the right filter. Today's protection is one well-tested layer, not defense-in-depth. **Retagged from `[MVP]` to `[BETA]`, found during this tracker's own final audit pass (2026-07-29):** this project has zero real external tenants today (one private network, one operator), and application-layer isolation is already real and tested with zero recorded failures — this is genuine defense-in-depth for a threat that hasn't materialized, not a closing correctness gap. Building it now, ahead of a real multi-tenant need, would be inconsistent with this project's own repeatedly-applied discipline of not inventing sophistication ahead of real need (the same reasoning already used to correctly defer search-relevance ranking, the event broker, and backpressure until each had a real trigger). `[BETA]` is the honest tag: build once real external tenants exist, not before.

### 7.1 Database-Level Row-Level Security `[BETA]`
- [ ] Postgres Row-Level Security (RLS) policies on the real tenant-scoped tables (`Resource`, `Slot`, `Booking`, `Rating`, `BookingAuditLogEntry` — anything keyed, directly or transitively, off `owner_ref`) as a genuine second layer, not a replacement for the existing application-layer checks
- [ ] A real, minimal session-variable mechanism (Postgres `SET LOCAL`, set once per request from the already-authenticated `BusinessAccount`/`Customer` context) so RLS policies have something real to filter on, without requiring a wholesale connection-pooling redesign
- [ ] **Real correctness risk, found during this tracker's own final audit pass, that must be resolved before this is safe to build, not discovered as a live data leak afterward:** Postgres `SET LOCAL` is scoped to the current transaction only. Both BAP's and BPP's `DATABASES` config already set `CONN_MAX_AGE` to a real, non-zero value (persistent connections, reused across requests) — if a request that sets the tenant session variable isn't wrapped in a real, explicit database transaction, `SET LOCAL`'s scoping guarantee doesn't hold: the variable could leak forward onto whichever *next* request happens to reuse that same pooled connection (a genuinely different tenant's request seeing a stale tenant context), or simply fail to apply at all, silently defeating the entire backstop this phase exists to add. This must be closed by wrapping every tenant-scoped request in an explicit transaction (e.g. Django's `ATOMIC_REQUESTS`, or a narrower per-view decorator if wrapping every request is too broad) *before* RLS policies are written, not assumed safe because the SQL itself is correct.
- **Test Gate:** `SEC` — a deliberately broken/forgotten application-layer filter (simulated by directly querying the DB with a different tenant's session context, bypassing the ORM's own `owner_ref` filter on purpose) is still correctly blocked by RLS at the database level; **the connection-pooling leak scenario above is explicitly tested, not just reasoned about** — two real, back-to-back requests from two different tenants, deliberately reusing the same pooled DB connection, are confirmed to never see each other's `SET LOCAL` context, proving the transaction-wrapping fix actually holds under Django's real `CONN_MAX_AGE` behavior, not just in a single-request unit test.
