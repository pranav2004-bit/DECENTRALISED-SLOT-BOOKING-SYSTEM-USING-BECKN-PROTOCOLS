## Design Principles (binding for every phase below)

These are not aspirational — each one is a concrete constraint later phases are graded against.

1. **Vendor-agnostic by construction.** One interface (`PaymentGatewayAdapter`: `charge()`, `refund()`, `verify_webhook()`, `get_status()`), N implementations. Proven, not assumed — Phase 5 exists specifically to build a *second* real adapter and demonstrate zero changes to core logic, the same way "no forked codebase" was proven, not just claimed, in `livetracker7.md`.
2. **The amount charged is never client-supplied, and never recomputed by the payment module.** The charge amount is read server-side, verbatim, from `SearchSession.confirmed_order["quote"]["price"]` (`BAP/backend/core/models.py:159` — the raw `/on_confirm` callback body BPP already sent, JSON, already populated by the existing confirm flow) — never from a value the frontend sends, and never re-derived independently from `Resource.price_value` (only BPP's `confirm_service.py` is allowed to compute a price; the payment module is a pure reader of BPP's own already-settled answer, so it can never disagree with BPP about what was quoted). This is the single most important correctness/security rule in this entire tracker — a tampered client must not be able to request a charge for less than what BPP actually quoted, and the payment layer itself must not become a second, independently-wrong source of truth for the amount.
3. **Idempotency is mandatory, not optional, on every money-moving call.** Every charge/refund carries a caller-generated idempotency key derived from the booking's own transaction ID, so a network retry or a double-click can never double-charge or double-refund. This is the payments-domain instance of the exact same "atomic operation, exactly-once" discipline `shared/inventory_core`'s capacity-decrement logic and `hold_multi_resource_booking`'s deterministic lock ordering already established in `livetracker2.md`.
4. **We never touch raw card data.** Hosted checkout / tokenization only (vendor's own hosted payment page or SDK-generated token) — this keeps PCI-DSS scope to SAQ-A, the minimal tier, by construction rather than by later audit. A design that requires our own servers to see a raw card number is rejected outright, not flagged for later review.
5. **Fail closed on trust, fail informative on UX.** A webhook with an invalid signature is rejected outright (never trusted "just this once"); a customer-facing payment failure always gets a specific, honest reason (`INSUFFICIENT_FUNDS`, `GATEWAY_TIMEOUT`, `DECLINED` — never a bare "something went wrong"), matching `API_CONVENTIONS.md`'s existing error-shape discipline.
6. **No new forked codebase, no new bespoke infra per vendor.** One `shared/payment_gateway` module, imported by BAP (primary collector) and BPP (settlement/refund awareness) — not copy-pasted into each, matching `livetracker7.md`'s own explicit "no new forked codebases" rule for the 5-participant work.

### 0.3 PCI-DSS Scope Decision
- [x] Confirmed: Razorpay's standard hosted-checkout integration satisfies Design Principle 4 (no raw card data ever touches this project's own servers) — [Razorpay hosted web integration best practices, official docs](https://razorpay.com/docs/payments/payment-gateway/web-integration/hosted/best-practices/).
- [x] Recorded PCI-DSS tier: **SAQ-A** — the lightest self-assessment tier, achievable specifically *because* card data is captured entirely on Razorpay's own hosted page, never on this project's servers. Confirmed via [PCI DSS scope reduction via hosted checkout, 2026](https://oneuptime.com/blog/post/2026-09-24-reduce-pci-dss-scope-hosted-checkout/view) and Razorpay's own PCI DSS Level 1 certification (merchants on hosted checkout inherit SAQ-A eligibility, not a deeper tier). This obligates the project to: never log/store/transmit raw card data anywhere in BAP/BPP code (already true — nothing today touches card data), and complete the (lightweight) SAQ-A self-assessment questionnaire before accepting real (non-sandbox) transactions. It does **not** obligate a PCI-certified server environment, network segmentation audit, or quarterly ASV scans (those apply to higher SAQ tiers this project deliberately avoids by construction).

### 0.4 Data Model Design
- [x] `PaymentTransaction` designed (fields below), living in the new `shared/payment_gateway/` module's own Django app (Phase 1.1 builds the actual file; this is the recorded field design):

  | Field | Type | Notes |
  |---|---|---|
  | `id` | UUIDField, PK | matches every other model's PK convention in this codebase |
  | `booking` | FK → `Booking`, `null=True`, `on_delete=SET_NULL` | mirrors `BookingAuditLogEntry`/`Rating`'s exact precedent — a payment record must outlive the booking row it was for |
  | `booking_id_text` | CharField, indexed | kept even if `booking` is nulled out — same precedent as above |
  | `amount` | DecimalField(10,2) | immutable once set (Design Principle 2 — read verbatim from `SearchSession.confirmed_order`/`Booking.confirmed_total_value`, never re-derived) |
  | `currency` | CharField | sourced alongside `amount`, never defaulted/assumed |
  | `vendor` | CharField | e.g. `"razorpay"` — which adapter handled this transaction |
  | `vendor_txn_id` | CharField, nullable | vendor's own order/transaction id; null until the charge attempt returns one |
  | `idempotency_key` | CharField, unique | derived from the booking's transaction id + attempt number — one row per real attempt, so a network-level retry of the *same* attempt hits the same row (deduped), while a genuine new attempt after a decline creates a *new* row with a new key |
  | `status` | CharField, choices | `PENDING` / `SUCCEEDED` / `FAILED` / `REFUNDED` / `PARTIALLY_REFUNDED` |
  | `refunded_amount` | DecimalField(10,2), default 0 | cumulative amount refunded so far — required to make `PARTIALLY_REFUNDED` auditable |
  | `collected_by` | CharField, choices `bap`/`bpp` | per §0.2, real protocol field values |
  | `created_at` | DateTimeField, auto_now_add | |
  | `succeeded_at` / `failed_at` / `refunded_at` | DateTimeField, nullable | full state-transition timestamps, per this task's explicit requirement — a heavier audit trail than `Booking`'s plain `created_at`/`updated_at`, justified here because this is a financial record |

- [x] State machine designed, mirroring `Booking.transition_status`'s exact edge-map pattern (`shared/inventory_core/models.py:238-243`, `_STATUS_TRANSITIONS`):

  ```python
  _PAYMENT_TRANSITIONS = {
      Status.PENDING: {Status.SUCCEEDED, Status.FAILED},
      Status.SUCCEEDED: {Status.REFUNDED, Status.PARTIALLY_REFUNDED},
      Status.PARTIALLY_REFUNDED: {Status.PARTIALLY_REFUNDED, Status.REFUNDED},
      Status.FAILED: set(),   # terminal — a retry creates a NEW row, never reopens this one
      Status.REFUNDED: set(), # terminal
  }
  ```

  `FAILED → SUCCEEDED` is explicitly not a valid edge on the same row (matches this task's own named example) — enforced by a new attempt always being a new `PaymentTransaction` row with a new `idempotency_key`, same discipline as `Booking.transition_status`'s `ValidationError`-on-invalid-edge behavior.

- [x] **Audit-identified subtask resolved: Option (a) chosen.** Add `Booking.confirmed_total_value`/`Booking.confirmed_total_currency` (nullable, written once by `confirm_service.py` at the same moment it computes `total_value` today, immutable after) — general-purpose fix, benefits `collected_by=BPP` (Phase 4.3), future reconciliation (§6.3), and closes the pre-existing gap that BPP's confirmed price is never persisted on its own side today. This is a Phase 1/4 implementation task (adding the migration + `confirm_service.py` write), not done in this Phase 0 research pass — recorded here so Phase 1 doesn't have to re-decide it.
- **Test Gate:** `SANITY` — state machine reviewed against every real flow named in Phase 3/4 below (happy path, decline, timeout, cancellation-triggered refund, partial refund) — every one of those flows maps onto a valid edge in `_PAYMENT_TRANSITIONS` above with no gap found; reviewed 2026-09-25, before any Phase 1 code exists, so the model shouldn't need a breaking migration mid-tracker.
