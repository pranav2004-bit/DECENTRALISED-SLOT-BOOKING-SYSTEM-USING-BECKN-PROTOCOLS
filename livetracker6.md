## How to Use This Tracker

1. **Part A before Part B, strictly — this is this tracker's one hard sequencing rule**, set explicitly by the project owner, not the usual "top to bottom where a dependency exists" latitude the other trackers allow. Do not start any Part B phase until every Part A phase's Exit checklist is closed.
2. Within Part A, Phase 1 (environment readiness) is pure verification/operational work and should be confirmed first — it determines whether *anything* is demoable, independent of what UI work is or isn't finished.
3. A task/subtask is checked `[x]` **only** after its implementation is complete **and** its Testing & Validation Gate passes. Never check a box on implementation alone.
4. A phase is closed **only** after its "Phase Exit — Testing & Sign-off" section is fully checked.
5. **Design-audit-before-implementing discipline, inherited from every prior tracker:** where a Part B item touches existing protocol behavior (e.g. §2.2's business order-review UI bordering on a real confirm-flow change), the scope ambiguity must be resolved and recorded *before* building, not discovered as a live regression. See §2.2's own recorded finding for a concrete example of this already happening once in this tracker.
6. If implementation reveals a decision not captured in a component's `*_details.md`, update that file in the same work session with an additive "Implementation note" callout — never rewrite the original client-provided content, and never touch `project_details.md`.
7. Lifecycle tags: Part A is `[MVP]` throughout (demo-critical, build/verify now). Part B is `[BETA]` throughout (the SaaS add-on platform vision — real, wanted, but explicitly not this tracker's near-term scope; do not build ahead of Part A closing).

### 2.2 Business-Facing Order-Review UI (BPP)
- [x] **Design-audit finding, recorded before implementing, per this tracker's own "How to Use" rule 5:** per confirmed Beckn protocol behavior, BPP already auto-acknowledges confirm/cancel synchronously — there is no "pending, awaiting business approval" state in the protocol flow this project implements today. A genuine pre-confirm approval gate would mean changing real confirm-handling logic to hold a booking pending business action — a materially different, larger change than a read-only list view, and a real behavior change to the already-tested, already-working confirm flow. **Scoped explicitly for this phase: a read-only Orders/Bookings list**, *not* a pre-confirm approval gate. The approval-gate version is named here as explicit future scope, not silently folded into this item or silently dropped.
- [x] **Staff-role scoping — the real, governing constraint for everything else in this subsection, stated first because the delivery design below is derived from it, not the other way around.** `livetracker3.md` Phase 8 already scopes a staff account to exactly one assigned resource (staff are redirected to their own resource's availability page, never the full owner dashboard). The Orders endpoint/page must apply that same real scoping — a staff account sees only orders for their assigned resource, an owner account sees every resource's orders.
- [x] **Real-time delivery via this project's own already-proven WebSocket mechanism, not polling.** `channels_redis`'s `RedisChannelLayer` (`livetracker2.md` §4.4) is real and working, but direct re-check of `BPP/backend/core/realtime.py` confirms its one existing channel group is strictly **per-resource** (`resource-{resource_id}-availability`). **Proof-status correction, found on this tracker's own eleventh self-audit pass: this bullet previously cited `livetracker4.md` §5.3 as having already "live-verified" this mechanism "at real multi-replica scale" — false.** Direct read of `livetracker4.md` §5.3 shows it is an unchecked `[ ]`, not-yet-run task, phrased in the future tense ("has only ever run as a single BPP instance... run two real BPP replicas... and confirm"), sitting inside Phase 5, one of the phases `RESUME_PROMPT.md` itself records as "designed but not yet started." What is actually proven (`livetracker2.md` §4.4) is correctness on a **single** BPP instance — real, but not the multi-replica claim this bullet borrowed. This doesn't block Part A (the demo runs one BPP instance, matching what's actually proven), but the false citation is corrected rather than left to imply a stronger guarantee than exists; §2.2's own new per-resource `-orders` groups inherit the same single-instance-proven, multi-replica-architecturally-correct-but-unverified status as the existing availability groups — not a new or different risk this item introduces.
- [x] **A serious design flaw found on this tracker's own fifth self-audit pass, in this tracker's own prior fix, not the codebase: a single per-business group is directly incompatible with the staff-scoping rule above.** The third/fourth-pass drafts of this item proposed one new `business-{owner_ref}-orders` group that every connection (owner or staff) would join — but a staff member joining a group covering *every* resource in the business would receive broadcasts for resources they're not supposed to see at all, the exact thing the staff-scoping rule exists to prevent. Filtering it back out client-side, after the browser already received it, would not be a fix — it's the standard anti-pattern of sending data to a client and trusting it not to look. **Corrected design: reuse the existing per-resource granularity, don't invent a coarser one.** A new, dedicated per-resource *order* group, `resource-{resource_id}-orders`, is broadcast to whenever a booking on that resource is `CONFIRMED`. A connection joins **exactly the resource groups the connecting account can actually access** — one group for staff (their one assigned resource, identical logic to the existing consumer), every owned resource's `-orders` group for an owner — so scoping is enforced by *which groups a connection is even allowed to join*, not by filtering what's already been delivered.
- [x] **The actual trigger mechanism, left unstated until this tracker's own seventh self-audit pass — a real gap, not a stylistic omission.** Direct re-check of `BPP/backend/core/realtime.py` and `BPP/backend/core/events_worker.py` confirms this codebase completed a deliberate architectural cutover (2026-08-02, recorded in `shared/inventory_core/consumers.py`'s own docstring): service-layer code (`select_service.py`/`cancel_service.py`/`update_service.py`) no longer calls any broadcast function inline at all — the *only* real trigger path left is publish-an-event → a consumer registered in `events_worker.py`'s own `DISPATCH` table reacts to it → that consumer calls the broadcast function (`broadcast_slot_update_consumer` → `broadcast_slot_update`, for the existing availability broadcast). §2.3 below, reacting to this exact same `BookingEvent.CONFIRMED` event, already correctly names this mechanism — this bullet did not, leaving an implementer free to wire the new order broadcast the old, now-deliberately-abandoned way (an inline call from confirm-flow service code), quietly reintroducing the coupling this project already paid down once. **Corrected: a new `broadcast_order_confirmed()` function (mirroring `broadcast_slot_update()`'s own shape) plus a new `broadcast_order_confirmed_consumer`, registered in `events_worker.py`'s `DISPATCH` table for `BookingEvent.CONFIRMED`** — alongside the `audit_log_consumer`/`booking_lifecycle_consumer` already there for that event type, composed via the existing `_combined()` helper, not a new, separate dispatch path.
- [x] **A real technical error found on this tracker's own sixth self-audit pass, in the fifth pass's own fix: its "or" alternative would have broken the already-working availability feature, not merely been a stylistic choice.** The fifth-pass draft floated putting the new order broadcast on the *same* group as the existing availability one, "since the transport already supports typed messages" — but direct re-check of `BPP/backend/core/consumers.py::ResourceAvailabilityConsumer.slot_update` confirms Django Channels routes a `group_send({"type": "slot.update"})` call to a method *named after the type* (dots become underscores — `slot_update` is that exact mechanism, not a coincidence of naming). Sending a *new* `{"type": "order.confirmed"}` message to that same group would make Channels try to call `order_confirmed()` on every already-connected `ResourceAvailabilityConsumer` instance — a method that doesn't exist, a real runtime error on every open availability-page connection the moment an order is confirmed on that resource. **This was never a safe equivalent to the dedicated-group option — removed as an alternative entirely.** The dedicated `resource-{resource_id}-orders` group (above) is the only correct design: a genuinely separate group, never mixed onto the one `ResourceAvailabilityConsumer` already owns.
- [x] **A new consumer class and URL route are required**, since `ResourceAvailabilityConsumer` is hard-coded to exactly one `resource_id` from its own URL route and can't join a variable number of groups (e.g. `BusinessOrdersConsumer` at `/ws/business/orders/`, registered in `bpp/asgi.py`'s own `websocket_urlpatterns` alongside `ResourceAvailabilityConsumer`'s existing entry) — on connect, it resolves the real, current set of resources the authenticated account can access: for an owner, a direct query (`Resource.objects.filter(owner_ref=...)`), not a loop calling `_resource_accessible_to` per candidate; for staff, that same existing single-resource check, reused exactly as `ResourceAvailabilityConsumer` already uses it, not a new, separately-invented permission rule — and joins exactly those resources' `-orders` groups, no others.
- [x] **Security discipline for the new consumer, inherited from this exact file's own real incident history, not left to be relearned.** `ResourceAvailabilityConsumer` needed three separate post-close fixes (`livetracker3.md` §8.1, its own docstrings) after shipping without them: re-validating access on every broadcast forward, not trusting the connect-time snapshot forever (a staff member unassigned mid-connection kept watching); and re-verifying the session's own auth hash (`channels.auth.get_user`), not just a stale `scope["user"]` object. The new consumer must build these in from the start — on a staff reassignment/unassignment, the connection must leave the now-inaccessible resource's group (`group_discard`) or close entirely, not keep receiving a group it joined under now-stale access.
- [x] **A new backend endpoint, named explicitly (not left implicit as "UI reads real rows"):** `GET /api/v1/orders` (or equivalent) on `BPP/backend`, scoped to exactly the same resource set as the WebSocket connection above (owner: all owned resources; staff: their one assigned resource — the same access-resolution logic, not a second, independently-written scoping rule) — returning real `Booking` rows with the same cursor-pagination shape already proven on the customer-side booking-history endpoint (`livetracker3.md` §9.1), for the initial page load the WebSocket then keeps live.
- [x] **Field name corrected on this tracker's own tenth self-audit pass.** Each row shows: the real Beckn transaction id (not raw customer PII, matching this project's own established IDOR-safety precedent for cross-trust-boundary references) — direct read of `shared/inventory_core/models.py`'s `Booking` confirms it has **no `transaction_id` column**; the value lives in `Booking.holder_ref` instead (confirmed by `BPP/backend/core/confirm_service.py`'s own ownership check, `booking.holder_ref != context["transaction_id"]` — `holder_ref` is where this BPP stores the transaction id it received the confirm under, not a customer identity, consistent with the model's own docstring: "opaque reference... not a foreign key"). The endpoint/serializer must read `holder_ref` and may rename it `transaction_id` in the API response shape for clarity, but the tracker itself must not send an implementer looking for a field that doesn't exist. Row also shows item/resource, slot time, current status.
