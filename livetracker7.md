# BECKN Platform — Multi-Participant Decentralization Live Tracker

> **Project scope declaration (2026-08-21), inherited from [livetracker1.md](livetracker1.md) (trust layer, closed), [livetracker2.md](livetracker2.md) (business workflow layer, closed), [livetracker3.md](livetracker3.md) (functional/UX gaps), [livetracker4.md](livetracker4.md) (infrastructure/scale-readiness), and [livetracker6.md](livetracker6.md) (vendor experience & client-demo readiness):** this project builds a **private, self-contained Beckn network** — our own Registry, Gateway, BAP, and BPP — that strictly follows the Beckn Protocol Specification and Beckn-ONDC Implementation Guidelines. `project_details.md` is never modified — it is the frozen, client-provided brief.

**Scope of this tracker:** Closes a gap the client raised directly (2026-08-21): today this network runs exactly **one** BPP participant and **one** BAP participant, each internally multi-domain via the domain-adapter pattern (`shared/inventory_core`, built `livetracker2.md` Phase 1). That's real, correct Beckn-protocol *capability* — but with only one participant on each side, the network's actual **decentralization and interoperability** property (many independent participants, freely discoverable and interoperable through the open protocol, no gatekeeper) has never been *demonstrated*, regardless of how many domains that one BPP happens to serve internally.

**The client's requirement, restated precisely:** three separate BPP participants, each scoped to exactly one domain (Medical/Healthcare, Automotive, Beauty — representing three different companies), and two separate BAP participants, each spanning all domains (representing two different companies competing for the same customers). This tracker builds that — as five real, independently-identified, independently-running instances, each with its own polished, distinctly-branded web UI, not backend-only.

**Explicit architectural finding this tracker starts from, verified live in code before any work began (2026-08-21):**
- `registry/core/models.py`'s `Participant` model already has a real `domain` field, unique per `(subscriber_id, domain, participant_type)` — Registry subscriptions are already genuinely per-domain, not a single flat participant record.
- `beckn-gateway/core/routing.py`'s `dispatch_search` already filters candidate BPPs by `domain` before dispatching — a BPP with no `SUBSCRIBED` row for a given domain is never looked up or routed to for that domain's search, under normal network traffic.
- **A real, independent gap found alongside this, not previously tracked anywhere:** `BPP/backend/core/search_service.py`'s `validate_and_ack_search` never checks the incoming request's `context.domain` against anything the BPP itself is configured for — `BPP/backend/core/apps.py` unconditionally registers all three domain adapters (Healthcare/Automotive/Beauty) on every instance, and there is no `SUPPORTED_DOMAINS`-equivalent setting anywhere in `BPP/backend/bpp/settings.py`. Today, "which domain(s) a BPP serves" is enforced at exactly **one** layer (Registry/Gateway filtering) — the BPP itself would still `200`-ACK a request for a domain it isn't meant to serve, and only fails to return matching businesses because none happen to exist in its own database for that domain. This is a real defense-in-depth gap, not a hypothetical — closed in Phase 1 below, before the multi-instance work that depends on "1 BPP = 1 domain" actually being true.

## How to Use This Tracker

1. Work phases **top to bottom, strictly** — this is a real dependency chain, not independent gap-closures like `livetracker3.md`/`livetracker4.md`. Phase 1 (BPP domain enforcement) must land before Phase 2 (new identities) can be trusted; Phase 2 must land before Phase 3 (data seeding) has anywhere correct to seed into; Phase 3 must land before Phase 4 (UI) has real data to display; Phase 4 must land before Phase 5 (cross-network proof) has anything to click through.
2. A task/subtask is checked `[x]` **only** after its implementation is complete **and** its Testing & Validation Gate passes, verified live against the real local Docker stack — matching every prior tracker's own standing discipline. Never check a box on implementation alone, and never record a Test Gate as passed without it actually having been run.
3. A phase is closed **only** after its "Phase Exit — Testing & Sign-off" section is fully checked.
4. **This is local-only work, matching `livetracker4.md`'s own explicit scoping discipline.** All 5 instances run on the existing local `docker compose` stack. Real cloud deployment (Vercel/Render/Supabase/etc., discussed separately with the project owner) is out of scope for this tracker entirely — this tracker makes the 5-participant topology real and demoable locally; deploying it to real infrastructure is its own later, separately-scoped decision.
5. **No new forked codebases.** Every new BPP/BAP instance is the *same* `BPP/backend`+`BPP/web` or `BAP/backend`+`BAP/web` codebase, differentiated only by deployment configuration (env vars: subscriber identity, signing keys, database, supported domain(s), brand/theme values) — reusing the domain-adapter architecture already built, not duplicating it. Any task that appears to require diverging the codebase per instance is a signal the design is wrong and should be reconsidered before implementing, not a normal/expected part of this work.
6. If implementation reveals a decision not captured in a component's `*_details.md`, update that file in the same work session with an additive "Implementation note" callout — never rewrite the original client-provided content, and never touch `project_details.md`.
7. Lifecycle tag: everything in this tracker is `[MVP]` — a direct, explicit client requirement, not speculative or scale-triggered work.

**Test type legend:** `SMOKE` basic runs · `SANITY` narrow correctness check · `FUNC` functional correctness · `POS`/`NEG`/`EDGE` case coverage · `INTEG` cross-service · `E2E` full flow · `SEC` security/abuse (incl. cross-participant isolation) · `REGR` regression.

## Phase 1 — BPP Domain-Scoping Enforcement `[MVP]`

**Objective:** Close the real gap found above before anything depends on "1 BPP = 1 domain" being true. Today, domain-scoping is enforced only by Registry/Gateway filtering; this phase adds a second, independent layer inside the BPP itself, so a single-domain BPP genuinely refuses out-of-scope requests rather than merely never receiving them under normal traffic.

### 1.1 `SUPPORTED_DOMAINS` Configuration
- [x] A new setting added to `BPP/backend/bpp/settings.py`, env-driven (matching this project's own established config pattern — `DOMAIN_HEALTHCARE`/`DOMAIN_AUTOMOTIVE`/`DOMAIN_BEAUTY` are already read from env there, lines 137-139): `SUPPORTED_DOMAINS = env.list("SUPPORTED_DOMAINS", default=[DOMAIN_HEALTHCARE, DOMAIN_AUTOMOTIVE, DOMAIN_BEAUTY])`. **Exact domain codes confirmed directly in code, not guessed:** Healthcare = `ONDC:SRV13`, Automotive = `BECKN:AUTO01`, Beauty = `ONDC:RET13` (`BPP/backend/bpp/settings.py:137-139`). The default preserves today's existing single-instance, all-3-domains behavior exactly, so this change is additive and non-breaking until a deployment's env file actually narrows it — e.g. BPP-Medical's env sets `SUPPORTED_DOMAINS=ONDC:SRV13` only. **Done 2026-08-21** — added at `BPP/backend/bpp/settings.py` directly below the existing `DOMAIN_*` settings; `BPP/backend/.env` left untouched (no `SUPPORTED_DOMAINS` line), so the default applies to today's combined instance.
- [x] `BPP/backend/core/apps.py`'s domain-adapter registration is left as-is (all three adapters stay registered in code) — narrowing *registration* is unnecessary and riskier than narrowing *request handling*; the adapters are generic, reusable code with no meaningful cost to keeping them loaded. **Confirmed 2026-08-21** — `apps.py` read directly, left unmodified; all three `register_adapter(...)` calls still unconditional.

### 1.2 Request-Boundary Validation
- [x] `BPP/backend/core/search_service.py`'s `validate_and_ack_search` (and any other action's own context-validation entry point that runs before Registry/Gateway would have already filtered it — i.e. anything reachable if a request bypasses Gateway and reaches this BPP directly) checks `context["domain"]` against `settings.SUPPORTED_DOMAINS` and returns a real NACK (not a silent empty-result ACK) for a mismatched domain — matching this project's own existing NACK envelope shape used elsewhere (`{"code": ..., "message": ...}`, per `livetracker4.md` §1.4's own cited example). **Done 2026-08-21** — new shared helper `BPP/backend/core/domain_scope.py` (`validate_domain_supported`/`DomainNotSupportedError`), called immediately after `validate_context` succeeds in **all ten** `validate_and_ack_*` entry points (`search_service.py`, `init_service.py`, `select_service.py`, `confirm_service.py`, `update_service.py`, `cancel_service.py`, `status_service.py`, `track_service.py`, `support_service.py`, `rating_service.py`) — every action a request could reach directly, not just `/search`. Each returns a 400 NACK with that action's own existing `{ACTION}_ERROR` code on a domain mismatch.
- [x] Confirm this check does not weaken or duplicate the existing `validate_context`/signature-verification checks already in place — it is a new, additional check, not a replacement for either. **Confirmed 2026-08-21** — inserted as its own `try`/`except DomainNotSupportedError` block, positioned after the existing context-validation block and before the existing `trust.verify_bap_and_gateway` block in every one of the ten files; neither existing check was edited or removed.
