## How to Use This Tracker

1. Work phases **top to bottom** — Registry is the network's single source of trust; nothing downstream (Gateway routing, BAP/BPP auth) can be trusted in production until Registry itself is. Gateway is the only thing every participant talks through, so it closes next and last — this tracker ends there. BPP/BAP production-readiness is a separate, later tracker, not part of this one.
2. A task/subtask is checked `[x]` **only** after its implementation is complete **and** its Testing & Validation Gate passes, verified live — matching every prior tracker's own standing discipline. Never check a box on implementation alone.
3. A phase is closed **only** after its "Phase Exit — Testing & Sign-off" section is fully checked.
4. **This tracker's endpoint is real cloud production**, unlike `livetracker7.md`'s explicit local-only scoping — so unlike that tracker, real infrastructure provisioning (Terraform, actual cloud accounts, DNS, TLS certs) is *in scope* here, not deferred.
5. Lifecycle tag: everything in this tracker is aimed at `[BETA]`/`[GA]` readiness — closing gaps this project's own docs already tag as blocking those tiers, not speculative work invented for this tracker.
6. If implementation reveals a decision not captured in a component's `*_details.md`, update that file in the same work session with an additive "Implementation note" callout — never rewrite frozen client-provided content.

**Test type legend:** `SMOKE` basic runs · `SANITY` narrow correctness check · `FUNC` functional correctness · `POS`/`NEG`/`EDGE` case coverage · `INTEG` cross-service · `E2E` full flow · `SEC` security/abuse · `PERF` load/latency · `REGR` regression.

## Phase 1 — Registry Production Hardening `[BETA]`

**Objective:** Registry is the network's single point of trust. Every gap below is either self-documented in this project's own code/docs as a pre-BETA blocker, or a real structural gap (no HA, no real cloud deployment) found during the 2026-09-03 audit.

### 1.1 Distributed Rate Limiting
- [x] Replace the in-memory (`LocMemCache`) rate limiter in `registry/core/rate_limit.py` with a shared, Redis-backed limiter. **Done 2026-09-03** — rather than reimplementing, `registry/core/views.py` now imports `rate_limit` from `shared/django_observability/rate_limit.py`, the same already-proven, already-battle-tested module BAP/BPP use (confirmed live by direct read: it already fixed the exact atomic-race and fail-open bugs Registry's own old module never had). `registry/core/rate_limit.py` deleted — fully superseded, zero remaining callers.
- [x] Add a `CACHES`/Redis config to `registry/registry/settings.py` — **Done 2026-09-03**, mirrors BAP's/BPP's own exact `CACHES` pattern (`django_redis.cache.RedisCache`, TESTING-mode DB-15 isolation). New `registry-cache` Redis service added to `docker-compose.yml` and `staged-up.sh` Stage 1; `django-redis`/`redis` added to `registry/requirements.txt`. CI needed zero changes — `.github/workflows/ci.yml`'s `test-python` job already ran a shared `redis` service with `REDIS_URL` set for the whole app matrix, registry included.
- [x] **Decide and implement explicit fail-open vs. fail-closed behavior when Redis itself is unreachable.** **Decided: fail-open, 2026-09-03** — matches this project's own established, hard-won convention (`shared/redis_safe/timeout.py`'s own docstring: "every caller here already treats a timeout the same as any other 'Redis unavailable' failure (fail open...)"), inherited automatically by reusing the shared `rate_limit` module rather than reinventing the decision.
- [ ] **This introduces Redis as a new hard dependency for Registry — scope its own production posture, not just the app code that talks to it.** Managed vs. self-hosted, persistence settings, and its own HA answer (feeds into §1.4) — don't fix one single point of failure by quietly introducing another with no plan. **Code-readiness confirmed 2026-09-04** — `django-redis`/`redis-py`'s own URL parsing already supports `rediss://` (TLS) with zero code changes, confirmed directly (`redis-py 5.2.1`, no custom connection-factory override anywhere in this config) — whatever managed Redis provider is eventually chosen, pointing `REDIS_URL` at its `rediss://` connection string just works. **The provider decision itself is still genuinely open** — this needs an actual account with a real provider (e.g. Upstash's free tier is the closest equivalent to what Neon is for Postgres here — genuinely free at this project's traffic scale, TLS by default, no credit card), which is an account-creation/budget action only the project owner can take, not something done unilaterally.
- **Test Gate:** `SEC`/`PERF`/`NEG` — **PASSED live 2026-09-03.** (1) 15 genuinely concurrent requests (`xargs -P 15`, real HTTP, not backgrounded shell jobs — the first attempt via `&`/`wait` was unreliable in this Windows/Git-Bash environment and was redone) fired at the real running `registry` container (gunicorn `--workers 2`) against `/subscribe`: exactly **10 succeeded (400, invalid payload but past the rate check) and exactly 5 got `429`** — the precise configured limit, correctly aggregated across both worker processes. Under the old `LocMemCache` bug, up to 20 could have gone through (10/worker × 2 workers) before any `429`. (2) Fail-open proven live, not just mocked: `docker compose stop registry-cache` (real container killed, not a code mock), then `POST /subscribe` still returned a real `400` (not a hang, not a 500) in 4.2s — the ~4s reflects `redis_safe`'s own documented DNS-resolution-against-a-stopped-container scenario, correctly bounded well under its 10s hard-timeout ceiling. Registry restored to healthy afterward. Unit-level coverage: 3 new tests (`registry/core/test_rate_limit.py`) covering both real Redis exception classes (`ConnectionInterrupted`, `redis.exceptions.ConnectionError`) and atomic concurrent counting (20 real threads, all individually counted). Full regression: registry **56/56 passed** (53 pre-existing + 3 new), 92% coverage.

### 1.2 Automated Key Rotation
- [x] Build a real key-rotation mechanism/runbook beyond "manually re-run Subscribe with a new keypair" (today's process, `SECURITY.md:27` — that process is for a *participant's* key anyway; Registry's own identity had no rotation mechanism at all before this). **Done 2026-09-04.** New `rotate_registry_keys` management command (`--key-type signing|encryption|both`), backed by `registry_service.rotate_registry_key` (writes a real `AuditLogEntry`, `subscriber_id="__registry__"`) and `registry_keys.rotate_signing_keys`/`rotate_encryption_keys` (backs up the old key with a timestamped filename before an atomic temp-file-then-`os.replace` overwrite — never destroys the only copy of a key without a recovery path, matching `CLOUD_KEY_PERSISTENCE.md`'s own backup-before-destructive-change discipline). Refuses to rotate a key that was never provisioned (`NoExistingKeyError`, clean `CommandError` from the CLI) rather than silently generating a first one.
- [x] **Real, previously-unnoticed bug found and fixed along the way**: `registry_keys.py`'s `get_registry_signing_keys`/`get_registry_encryption_keys` had an `@lru_cache(maxsize=1)` since this module's original design — meaning a rotation would write the new key to disk but every already-running gunicorn worker would keep serving the *old* key from its in-process cache until restarted, directly contradicting the "zero window" requirement below. Removed — not a hot path (confirmed: not called from the Subscribe/Lookup request flow, only `/identity` and onboarding), so re-reading a small JSON file per call is cheap and now correctness-first.
- [x] **A real, defined rotation cadence, enforced automatically — not just a mechanism a human has to remember to invoke.** Found as a real, self-identified gap on 2026-09-04 re-audit: the original build only delivered the *mechanism* (the command), not the actual "doesn't depend on a human remembering" requirement — nothing scheduled it. **Closed 2026-09-04**: `REGISTRY_KEY_ROTATION_DAYS` setting (default 90 — a standard industry baseline for API/signing key rotation, documented in `SECURITY.md`), `registry_keys.is_rotation_due`/`key_age_days` (keyed off the key file's own mtime, no separate state to invent), and the command now only actually rotates once a key is genuinely due — safe to invoke on any schedule without over-rotating. The actual always-on trigger: a new `registry-scheduler` service (`mcuadros/ofelia`, ~15MB, Docker-native cron) reading `ofelia.*` labels on the `registry` service (`docker-compose.yml`) to run the command daily. Deliberately not a new full worker microservice — the job runs a few times a year at most, a dedicated service would be over-engineering for that. Cloud-provider-agnostic: identical mechanism regardless of what §1.6 eventually lands on, so this didn't need to wait on that decision.
- [x] **The encryption-key rotation race, traced and proven safe, not just assumed.** Found on further self-audit (2026-09-04): a participant fetches Registry's *current* encryption public key fresh, at decrypt time, from inside their own `/on_subscribe` handler (confirmed by direct read of `BAP/backend/core/onboarding_service.py::handle_on_subscribe` — not cached in advance). If a rotation lands between Registry encrypting the challenge and the participant's own fresh fetch, decryption fails. Traced the real bound on that window: `registry_service.py::handle_subscribe`'s own docstring — "synchronously dispatch... before returning" — the entire Subscribe→challenge→verify round trip completes within one HTTP request, not an open-ended window. New test (`registry/core/test_subscribe_flow.py::test_subscribe_fails_safely_if_registry_encryption_key_rotates_mid_challenge`) proves the failure mode when it does happen: rotates the real encryption key from inside the mocked participant's own callback (simulating the rotation landing exactly in that gap), confirms decryption genuinely fails (`ChallengeDecryptionError`, matching real BAP/BPP/Gateway's own unhandled-exception behavior — none of them catch this), and confirms Registry handles it cleanly — no crash, participant stays `UNDER_SUBSCRIPTION`, real audit trail (`ON_SUBSCRIBE_DISPATCH_FAILED`), safe to simply retry Subscribe. Not a security hole (no data exposure, no auth bypass) — an availability edge case, now proven bounded and safe rather than left as an unverified assumption.
- **Test Gate:** `FUNC`/`SEC` — **PASSED live 2026-09-04.** Rotated the real signing key on the actual running container (`docker compose exec registry python manage.py rotate_registry_keys --key-type signing --force`) — `GET /identity` returned the genuinely new public key on the *very next request*, same running container, zero restart: before `teNsf75AjdQD...`, after (first rotation) `rjYhXhOQyw1G...`, after (second, testing the cadence logic) `LKxMRsObwV/L...`. Backup files confirmed on disk with the exact pre-rotation key inside each time. Encryption key confirmed untouched when only `--key-type signing` was requested. **Cadence enforcement proven live, both directions**: a plain unforced invocation (the exact command the scheduler runs daily) against a recently-rotated key correctly printed "not due for rotation yet... skipping" and left the key genuinely unchanged; `--force` correctly bypassed that and rotated for real. **Scheduler proven live**: `registry-scheduler`'s own log shows `New job registered "rotate-registry-keys" - "python manage.py rotate_registry_keys" - "@daily"` — confirms the ofelia sidecar genuinely discovered and parsed the labels on the real running `registry` container, not just a config file that was never read. 12 new tests total (`registry/core/test_key_rotation.py`, expanded from the original 6): no-existing-key refusal, replace+backup, audit log entry written, management command rotates both by default, clean `CommandError` on nothing-to-rotate, encryption rotation, key-age calculation (missing/fresh/backdated-to-simulate-old), due-check true/false logic, command skips an undue key without `--force`, command rotates a due key without `--force` (the actual scheduler-facing path). Full regression: registry **68/68 passed**, 93% coverage — on the freshly rebuilt Docker image, not just files copied into a running container.

## Phase 2 — Gateway Production Hardening `[BETA]`

**Objective:** Gateway is the only thing every participant talks through for discovery. It's structurally ahead of Registry (Redis-backed circuit breaker on by default, per-participant breaker isolation), but shares Registry's HA/secrets/deployment gaps and has one gap of its own.

### 2.1 Mandatory Circuit Breaker / Cache
- [x] `beckn_gateway_details_v1.1.md:39` documented the Redis-backed cache/circuit breaker as architecturally **optional** (`CACHE_ENABLED` toggle) — without it, a Registry outage takes ~19s to fail on *every single request* across all gunicorn workers instead of failing fast (`beckn_gateway_details_v1.1.md:45`). BAP/BPP already made their own equivalent mandatory; Gateway now matches. **Done 2026-09-04** — `CACHE_ENABLED` removed entirely from `gateway/settings.py`; `REDIS_URL` is now a required setting with no default (matching BAP's/BPP's own pattern exactly); `core/registry_client.py`'s `get_client()`/`get_participant_client()` construct the Redis client unconditionally — the old `if settings.CACHE_ENABLED and settings.REDIS_URL:` gate is gone, no code path left that runs without it. `.env`/`.env.example` and `beckn_gateway_details_v1.1.md`'s own Implementation note updated to drop the "optional"/"purely a resilience concern, not required for correctness" framing.
- **Test Gate:** `SEC`/`PERF` — **PASSED live 2026-09-04.** Stopped the real Registry container, sent 6 consecutive real searches through the running stack (BAP-X → Gateway → Registry lookup) and timed each: **8.4s → 3.5s → 3.5s → 3.5s → 0.56s → 0.57s** — a clear trip point once the breaker's failure threshold was reached, then consistent sub-second fast-fail afterward (a 6-15× speedup, matching the exact `CircuitOpenError` behavior this Test Gate asks for). Restarted Registry and confirmed fast, automatic recovery — the very next search succeeded (`202`, genuinely dispatched) once the breaker's half-open probe found Registry healthy again. Full regression: Gateway **34/34 passed**, 89% coverage, on the freshly rebuilt image.

### 2.2 Automated Key Rotation
- [x] Same gap as Registry §1.2 — Gateway's own identity key is rotated manually today. Build the same real mechanism, ideally shared tooling between Registry and Gateway rather than two separate implementations. **Done 2026-09-04.** Extracted the generic backup/atomic-write/due-check primitives into a new `shared/key_rotation` module — used by *both* `registry_keys.py` (refactored) and Gateway's `participant_keys.py`, closing the literal duplication the task named. Gateway already had a rotate-and-re-Subscribe command (`onboarding_rotate_keys`) that this tracker didn't originally know about — investigated it rather than assuming a blank slate, and found it had the exact same `@lru_cache` cross-process staleness bug as Registry's original §1.2 issue, plus a real, more serious one: it wrote new keys to disk *before* re-Subscribing, so a rejected re-Subscribe left Gateway signing with a key Registry never learned about. Redesigned: new keys are generated in memory and submitted to Registry first; disk is only written *after* Registry confirms the new identity — so a failure needs no rollback, because nothing was ever written.
- [x] **Same cadence mechanism as Registry** — `KEY_ROTATION_DAYS` setting (90-day default), `is_rotation_due`, `--force` override. The existing `key-rotation-scheduler` (renamed from `registry-scheduler`) needed no second instance — ofelia's daemon reads labels from *every* container on the Docker socket, so one scheduler now runs both `registry`'s and `beckn-gateway`'s rotation jobs (confirmed live: its own log shows "Starting scheduler with 2 jobs").
- [x] **Three further real, previously-hidden bugs found and fixed via this same live testing, not assumed away:**
  1. **Split-key signing requirement for the re-Subscribe itself.** Registry's `verify_subscribe_authorization` requires a re-Subscribe's Authorization header to be signed with the *currently registered* (old) key, not the new one — confirmed directly against `registry_service.py`'s own docstring and `RUNBOOK.md`'s "Known Operational Facts". The original design (rotate-then-Subscribe) signed with the new key and got a correctly-rejected `401`. Fixed: `onboarding_service.submit_subscribe` now accepts explicit `signing_public_key`/`encryption_public_key` overrides for the *payload*, while the actual HTTP signing still reads whatever's on disk (the old key, untouched until confirmed).
  2. **The identical split for the encryption key, one layer deeper.** Registry's on_subscribe challenge dispatch — itself part of the *same* synchronous Subscribe handling — encrypts the challenge with the *new* encryption public key just submitted. Gateway's own `/on_subscribe` callback needs the matching new *private* key to decrypt it, arriving as a genuinely separate HTTP request (confirmed live as a real `400 Bad Request` before the fix). Solved with a short-TTL (60s), Redis-backed hand-off (`set_pending_rotation_signing_key`/`set_pending_rotation_encryption_key`) — not an in-process variable, since Registry's callback can land on a different gunicorn worker than the one running the rotation command. **This surfaced its own real bug**: Gateway had no `CACHES` setting at all, so `django.core.cache.cache` silently defaulted to per-worker `LocMemCache` — confirmed live (a key set from a separate process was invisible to the worker serving the real HTTP request) and fixed with the same Redis-backed `CACHES` block Registry already has.
  3. **A pre-existing status-tracking race, unrelated to rotation specifically but found via this same Test Gate.** `BAP/backend/core/onboarding_service.py` already documents and guards against Registry's `/subscribe` response always literally saying `"UNDER_SUBSCRIPTION"` regardless of what actually happened — Gateway's own copy of `submit_subscribe` never got either half of that fix. Confirmed live twice: first a successful rotation left Gateway's local state wrong (Registry said `SUBSCRIBED`, Gateway's own file still said `UNDER_SUBSCRIPTION`); after the "don't downgrade" guard alone, still wrong (nothing to flip, since the row was never marked `UNDER_SUBSCRIPTION` before the call). Both halves of BAP's already-established fix ported over.
- **Test Gate:** `FUNC`/`SEC` — **PASSED live 2026-09-04**, on the real running stack, against the real running Registry (not mocked). Rotated Gateway's real signing+encryption keys end-to-end: command reported `Re-Subscribed ONDC:RET13 with rotated keys: SUBSCRIBED`; Gateway's own local state independently confirmed `{'status': 'SUBSCRIBED', ...}`; Registry's own authoritative `Participant` row independently confirmed the exact same new public key with `status=SUBSCRIBED`. Due-check proven: an unforced invocation right after correctly skipped ("not due... skipping"). Scheduler proven: `key-rotation-scheduler`'s log shows both jobs registered and running from one instance. Full regression: Gateway **46/46 passed**, 91% coverage, on the freshly rebuilt image — 5 new tests directly covering the 3 bugs above (split-signing-key proof, split-encryption-key proof, both halves of the status-race fix), on top of the original rotation/backup/restore tests.
