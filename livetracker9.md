# Doctor/Item Availability-by-Date Filtering — Live Tracker

> **Project scope declaration (2026-10-25), inherited from [livetracker1.md](livetracker1.md) (trust layer, closed), [livetracker2.md](livetracker2.md) (business workflow layer, closed), [livetracker3.md](livetracker3.md) (functional/UX gaps), [livetracker4.md](livetracker4.md) (infrastructure/scale-readiness), [livetracker6.md](livetracker6.md) (vendor experience & client-demo readiness), and [livetracker7.md](livetracker7.md) (multi-participant decentralization):** this project builds a **private, self-contained Beckn network** — our own Registry, Gateway, BAP, and BPP — that strictly follows the Beckn Protocol Specification and Beckn-ONDC Implementation Guidelines. `project_details.md` is never modified — it is the frozen, client-provided brief.

**Scope of this tracker:** closes a real gap the project owner raised directly (2026-10-25) while reviewing the search-results UI: once drilled into a provider's (hospital/salon/garage) item list, every item (doctor/stylist/mechanic) was shown regardless of whether it genuinely had any bookable slot — a customer could tap "Book appointment" on an item with nothing actually open, only discovering that at `/select`. This tracker adds a real, signed, per-date availability check between BAP and BPP so the search-results UI only ever renders items that genuinely have an open slot on the selected date, and extends the same real-slot-list idea to `/select`'s own time picker (a free-text time input, previously — a customer could request any arbitrary time, not just a real one).

**Not a real Beckn action.** Neither `check_availability` nor `list_available_slots` has a protocol-schema counterpart — the real Beckn spec has no "list available dates/slots" action (same "project-defined, not protocol-confirmed" territory as the `Slot` model itself, `shared/inventory_core/models.py`'s own docstring). Both are shaped and verified exactly like the other direct BAP↔BPP calls this project already has (`payment_status_service.py`'s own module docstring: real registry-trust signature verification, never a bespoke REST auth scheme) — but answer **synchronously**, not via a later `on_X` callback: both are read-only, no-side-effect queries already fully resolved by the time an ack would be sent, so select/init/confirm's async ack-then-callback shape would only add latency here for no benefit.

**Related documents (this repo):** [project_details.md](project_details.md) · [livetracker2.md](livetracker2.md) (original search/select/init/confirm flow this extends) · [livetracker7.md](livetracker7.md) (the 5-participant topology this ships against) · [BPP/BPP_details_v1.1.md](BPP/BPP_details_v1.1.md) · [BAP/BAP_details_v1.1.md](BAP/BAP_details_v1.1.md) · [RUNBOOK.md](RUNBOOK.md)

**Audit grounding:** scoped directly from the project owner's own description of the problem (2026-10-25), then verified against real, current code (`shared/inventory_core/models.py`'s `Slot`, `BPP/backend/core/catalog.py`'s `visible_resources`, `BAP/backend/core/select_service.py`'s direct-dispatch pattern) before implementing — every design decision below mirrors an already-established pattern in this codebase, not a new one invented for this feature alone.

## Phase 1 — Availability-by-date check (search-results filtering) `[MVP]`

### 1.1 BPP: `check_availability` endpoint
- [x] `BPP/backend/core/availability_service.py` — new module. `check_availability()` validates + verifies the calling BAP (`trust.verify_bap_and_gateway(..., require_gateway=False)`, same as `on_select`'s own direct-from-BPP shape), then answers per `resource_id` whether it has a real `AVAILABLE` slot with `capacity_remaining > 0` on the given **IST calendar date** (this is an India-only platform — `ALL_INDIA_STATES` is the entire location model — so "today"/"this date" means the IST wall-clock day, converted to the UTC storage `shared/inventory_core/models.py` already uses, not reinterpreted per caller). Excludes already-ended slots for today (`end_time > now`). A malformed/out-of-domain/paused-business `resource_id` is answered `False`, never omitted and never distinguished from a genuine "no slots today" — a uniform "no" leaks nothing about *why*, and one bad id in an otherwise-valid batch must never fail the whole request. **Done 2026-10-25.**
- [x] Defense-in-depth ceilings: `MAX_RESOURCE_IDS = 50` per call, `MAX_DAYS_AHEAD = 60`. **Done 2026-10-25.**
- [x] `check_availability_view` + `/check_availability` URL, `@rate_limit(limit_per_minute=60, scope="bpp-check-availability")` — matching `rating_view`'s/`support_view`'s own IP-keyed defense-in-depth tier, a bit more generous since picking a date is a natural multiple-times-a-minute gesture, not a one-off action. **Done 2026-10-25.**
- [x] Metrics: `bpp_availability_check_total{outcome="succeeded"|"rejected"}`, a separate family from `bpp_booking_lifecycle_total` — a read with no booking-lifecycle outcome has no honest place among hold/confirm/cancel counts. **Done 2026-10-25.**

### 1.2 BAP: `check_doctor_availability` customer-facing trigger
- [x] `BAP/backend/core/availability_service.py` — new module, mirrors `select_service.py`'s own direct-dispatch pattern exactly (fresh Registry lookup immediately before dispatch, never a client-supplied destination URL; `_find_provider_bpp` mirrors `_find_item_provider`'s exact anti-IDOR discipline — a `resource_id` outside this session's own real `on_search` results for the given `provider_id` is silently dropped before anything is ever sent to a BPP, never used as a probe for an arbitrary id on an arbitrary BPP). **Done 2026-10-25.**
- [x] **Batches, never truncates**, when a provider has more items than one BPP call's own `MAX_RESOURCE_IDS` cap — split into several signed calls, merged. A later batch's failure is logged, not raised, so one bad batch doesn't erase genuine answers earlier ones already got. **Done 2026-10-25** (found live during this same session's own review: the first version silently truncated past 50; fixed before shipping, see Change Log).
- [x] `check_availability_view` (`POST /api/v1/search/<transaction_id>/availability`) + `@rate_limit(limit_per_minute=30, scope="check-availability")`. **Done 2026-10-25.**
- [x] Metrics: `bap_availability_check_total{outcome="succeeded"|"failed"}`. **Done 2026-10-25.**

### 1.3 Frontend: search-results filtering
- [x] `BAP/web/app/search/page.tsx` — fetches availability per `(providerId, date)` whenever either changes, cached (flipping back to an already-checked date is instant, no refetch), race-safe (`cancelled` flag, matching every other async effect already in this file). Only an item the fetch marks `true` ever renders — hidden outright, not shown disabled, per the project owner's own explicit instruction ("no need to show the expired doctors slots"). Distinct loading / error-with-retry / "availability not updated" empty states — the last one uses the existing `DOMAIN_NOUNS` map so the copy reads correctly across Healthcare/Wellness/Automotive ("Hospital hasn't updated doctor availability for this date yet," not a hardcoded "doctor"/"hospital" that would be wrong outside Healthcare). **Done 2026-10-25.**
- [x] **Real bug found and fixed live, same session:** the availability-fetch effect was first keyed to the `selectedProvider` object itself, which gets a brand-new reference on every background search-poll tick (`providerGroups` rebuilds from a fresh `data` object each `usePoll` interval, even when content is unchanged) — this re-fired the fetch roughly every 1.5s while "Still checking for more providers…" was still active, not just on a genuine provider/date change. Fixed by keying the effect to the stable `selectedProviderId` string and reading the live item list via a ref — the exact same failure class (and same fix shape) `components/shell/HeaderContext.tsx`'s own docstring already documents from an earlier incident this same project hit. **Verified live**: confirmed via `read_network_requests` that exactly one request fires per genuine date/provider change, not a burst.

## Phase 2 — Real slot-time picker (`/select`) `[MVP]`

**Objective:** close a second instance of the same underlying problem, one step later in the funnel — even after Phase 1 only shows items with *some* open slot that day, `/select`'s own time field was still a free-text `<input type="time">` with no floor beyond "not in the past" — a customer could still request a time that was never actually a real slot, only finding out after submitting.

### 2.1 BPP: `list_available_slots` endpoint
- [x] `BPP/backend/core/availability_service.py` — `list_available_slots()`, same trust/validation discipline as 1.1, but for **one** `resource_id` + one date, returning the real `[{start_time, end_time}]` list (`MAX_SLOTS_RETURNED = 200`, a defensive ceiling — a real day never has anywhere near that many bookable windows for one resource). Same uniform-non-leaking answer as 1.1: an invalid/out-of-domain/paused resource gets `[]` back (200), not a 404/400 that would reveal which. **Done 2026-10-25.**
- [x] `list_available_slots_view` + `/list_available_slots` URL, same rate-limit tier as 1.1. **Done 2026-10-25.**

### 2.2 BAP: `list_doctor_slots` customer-facing trigger
- [x] Same anti-IDOR discipline as 1.2 (`resource_id` must genuinely belong to `provider_id` per this session's own real results). `list_available_slots_view` (`POST /api/v1/search/<transaction_id>/slots`). **Done 2026-10-25.**

### 2.3 Frontend: real time picker
- [x] `BAP/web/app/select/page.tsx` — the `<input type="time">` replaced with buttons rendering each real slot's `formatTime(start_time)`; submission uses the chosen slot's own `start_time` directly (no more combining a separately-typed date+time string). `provider_id` added to the `Link` query from `search/page.tsx` (previously not passed — `/select` had no way to resolve which BPP/provider a bare `item_id` belonged to for this new call). Loading/error-with-retry/no-open-times states, same shape as Phase 1's. **Done 2026-10-25.**
- [x] `BAP/web/components/ui/DateStrip.tsx` extended with an `edgeToEdge` display option (full-bleed, no rounding/side borders) for the search-results page's date strip, reused as-is (default rounded-card look) on `/select`. `minTimeForDate` (no longer needed once only real future slots are ever offered) left exported but unused by `/select` — harmless, not removed, since nothing else references it yet either way.

## Phase 3 — Pre-existing bugs found and fixed along the way `[MVP]`

Not this tracker's original scope — found live while verifying Phase 1/2 against the real full BPP test suite, at the project owner's explicit instruction ("production ready... no gaps left behind"). All three were **stale test assertions**, not production bugs — in every case the real implementation was already correct; the test simply predated a later, correct fix and was never updated to match it.

- [x] **`test_business_account_generates_real_slots_via_availability_calendar`** (`BPP/backend/core/test_business_account.py`) — asserted a generated slot's stored UTC hour equals the IST wall-clock hour requested (e.g. "09:00" → `hour == 9`), which only the *pre-fix* (buggy, since-corrected 2026-10-20) behavior would ever satisfy. `shared/inventory_core/models.py`'s `generate_slots()` already correctly converts IST → UTC (9:00 AM IST → 03:30 UTC, exactly what the test observed and incorrectly failed on). Fixed to assert against `start_time.astimezone(ZoneInfo("Asia/Kolkata")).hour` instead of a raw UTC magic number — self-documenting and won't silently re-break the next time this is touched. **Fixed and verified 2026-10-25.**
- [x] **`test_deactivated_business_accounts_resources_disappear_from_catalog`** — `resources-list` deliberately reflects real catalog/search visibility (its own docstring), which requires `is_accepting_bookings` — a fresh signup defaults to `False` (`BusinessAccount.is_accepting_bookings`'s own docstring: an empty profile can't go "Live" the instant an account is created). The test never flipped it, so its very first assertion (before any deactivation) was already checking a business that was never visible to begin with. Fixed by explicitly setting `is_accepting_bookings=True` after signup. **Fixed and verified 2026-10-25.**
- [x] **`test_healthcare_business_creates_a_doctor_resource`** — `HealthcareDomainAdapter.validate_resource_domain_data` requires `specialisation`/`education`/`years_of_experience`/`gender` on top of `resource_type` (a real, deliberate requirement — its own comment: a doctor listing without them is the exact "not enough information to book" complaint real ONDC health listings get flagged for). The test only ever sent `resource_type`. Fixed by supplying all four required fields; the final assertion also updated to account for `resource_create_view`'s own server-generated `doctor_id` (never client-supplied, same as `owner_ref`). **Fixed and verified 2026-10-25.**

**Verification discipline note:** the first full-suite run (pre-fix) reported "397 errors" — investigated rather than reported as-is, and traced to this session's own overlapping background test containers contending for the same live Neon Postgres connection, not a real code problem (confirmed by re-running the same file in true isolation: clean). The three bugs above were only trusted as real once reproduced in isolation, twice.
